# AI 统一网关架构复杂度评估（只分析，不改代码）

> 背景：AI 底座与调用场景链路梳理完成后，对"统一网关本为简化，现在是否反而维护更多"的质疑做一次客观盘点。
> 结论先行：**方向是对的，收益真实；但当前处于"半收口"过渡态，最痛的维护点恰恰是过渡产物，而非网关本身。**

---

## 1. 先回答核心问题：简化了吗？

分两个时间维度看：

**如果收口彻底完成（目标态）**——是简化：
- 11 个场景共用一套安全防护 / 限流 / 熔断 / 缓存 / 降级 / 日志，业务 Service 只剩"调一个方法 + 写兜底"；
- LLM 对接只在 ext.ai 一处，换模型/换提供商改配置不改代码。

**当前现状（过渡态）**——局部确实更复杂了：
- 收口了一半，另一半（面试主干、管理端平台能力）还在外面平行运行；
- 为了让外面的部分"看起来在治理范围内"，又加了灰度开关、治理前置、双客户端入口等粘合层。

**一句话：不是网关设计错了，是收口做了一半——一半收口的系统永远比全收口或全不收口更乱。**

---

## 2. 复杂度账本：现在到底要维护多少东西

### 2.1 平行运行的两套 LLM 调用体系（最大的乱源）

| | 统一网关体系（aiapp） | 平行体系（不经网关） |
|---|---|---|
| 入口 | `/api/ai/execute`(+stream) | `/cms/ai/chat/stream`、`/portal/interview/voice/{id}/answer`、`/cms/ai/diagram/chat/stream` |
| 调用方 | 11 个场景 Handler | `DynamicChatService`（管理端对话）、`InterviewAgentClientImpl`（面试主干）、`DiagramChatService`（图表） |
| 模型选择 | AiSceneResolver（场景→模型） | per-agent / 直连 |
| 会话记忆 | 无（单次调用抽象） | `InterviewChatMemoryService` / `RedisChatMemoryStore` |
| 治理 | 五层编排全套 | 面试靠灰度开关前置；管理端对话基本无网关治理 |

**问题本质**：这不是"一个网关 + 一个特例"，而是"任务型调用网关"和"会话型对话引擎"两个正交需求，目前用两套代码各自满足。网关的 `AiExecuteRequest`（单次、无状态）天然装不下"多轮 + 记忆 + 流式 + per-agent"。

### 2.2 特例的粘合成本（面试主干直连）

围绕这一个特例，当前要维护：
1. `InterviewAgentClientImpl` 里的直连调用 + 同步模拟流式兜底；
2. 灰度开关 `ai.gateway.interview.enabled` 的两套行为分支；
3. 治理前置逻辑（复用 voice_interview 场景行参数 + handler 记为 interviewMainTrunk）；
4. 治理组件异常时的降级放行；
5. 网关侧 voice_interview 场景行（限流/熔断参数与直连共享）。

**本来一个调用，现在背了 5 个概念。** 这是典型的"用胶水代码模拟统一"——表面收口，实际两头都要懂。

### 2.3 配置的三层四源

| 来源 | 生效方式 | 管理位置 |
|---|---|---|
| `ai_scene_config` | 直查库，即时生效 | 管理端 /cms/ai/scene |
| `ai_model_config` / `ai_provider` / `ai_agent` | Redis 缓存 + 主动失效 | 管理端各自 Controller |
| `sys_config`（ai.global.enabled 等 3 个开关） | 热配置 | 系统参数管理 |
| yaml（moyun.ai.* / moyun-ai.*） | 重启生效 | 配置文件 |

排障时一个问题可能要查四个地方。且存在历史遗留：`AiProperties`（早期 yaml 静态配置）与 `AiGlobalSwitch`（sys_config 热开关）双轨，前者已边缘化但仍在。

### 2.4 双入口、双命名、双异步

- **双入口**：`AiSceneJsonClient`（失败返 null）vs `AiGatewayService.execute`（拿完整元数据）——这条是合理分层，不算乱；
- **双命名**：包名 aiapp / 测试包名 ai2 / 日志前缀 [ai2:]——纯历史包袱，增加认知成本；
- **双异步**：表驱动（portal_ai_task，4 种任务）vs Redis+线程池（财务分析）——有"留痕 vs 轻快"的设计理由，但两套心智模型并存。

### 2.5 task 子任务契约的隐性复杂度

一个 Handler 内用 `input.task` 路由多个子任务（resume_optimize 4 个、voice_interview 3 个），提示词全部收编在 Handler 里。**好处**是业务侧不拼 Prompt；**代价**是：
- Handler 变成大杂烩（VoiceInterviewHandler 承载 3 种不同输出结构）；
- 子任务没有独立配置行——想单独调某个 task 的温度/限流做不到，只能整场景共享；
- 读代码时要先知道有哪些 task 值才能理解 Handler 分支。

## 3. 收益账本：如果不做网关会怎样（反事实推演）

假设 11 个场景各自直调 LLMService，需要每个业务 Service 各自实现：

| 能力 | ×11 场景重复实现 | 网关统一后 |
|---|---|---|
| Prompt 注入防护（双通道+对抗绕过） | 11 处，且容易漏 | PromptInjectionGuard 一处 |
| 限流 / Token 熔断 / 成本核算 | 11 处 | 一处，配置驱动 |
| 执行日志 / requestId 追踪 | 大概率没有 | ai_execute_log 全覆盖 |
| 降级兜底（fallback_response） | 各写各的 | FallbackStrategy 统一 |
| 提示词变更 | **改代码发版** | 管理端改配置即时生效 |
| 换模型/提供商 | 各处改 | 配置表改 |

**安全收口的价值尤其真实**：注入防护这种东西，散落 11 处必然出现薄弱点。这是当初收口最硬的理由，现在依然成立。

## 4. 复杂度定性：哪些是固有的，哪些是自找的

### 本质复杂度（LLM 应用固有，删不掉）
- 多场景差异化策略（每场景不同提示词/模型/限流）→ ai_scene_config 是合理答案；
- 安全防护、成本控制、降级 → 网关五层编排是合理答案；
- 流式 SSE、RAG、多轮记忆 → 需求本身就在。

### 偶发复杂度（过渡期债务，可以消除）
| # | 债务 | 消除条件 |
|---|---|---|
| D1 | 面试主干直连 + 灰度开关 + 治理前置（5 个概念） | 网关支持会话型流式（多轮+记忆+per-agent） |
| D2 | DynamicChatService（管理端对话）独立一套 | 同上，会话能力下沉网关后可合并 |
| D3 | ai2/aiapp 双命名 | 一次性重命名，纯体力活 |
| D4 | AiProperties 与 AiGlobalSwitch 双轨 | 删 AiProperties 残留 |
| D5 | task 子任务挤在单 Handler | 拆配置行（每个 task 一行 ai_scene_config，场景码加后缀）或接受现状 |
| D6 | PortalAiController 注释里的 TODO（薄化为仅调 AiSceneJsonClient） | 小改动 |

**关键观察：最痛的 D1/D2 指向同一个缺口——网关缺"会话型流式"能力。补上它，两大平行体系可以真正合一；补不上，粘合层会一直滋生。**

## 5. 维护负担的实际分布（新增一个 AI 能力要动几处）

**走网关新增场景（收口内的世界）**：
1. `AiSceneEnum` 加枚举（1 行）
2. 实现 `AiSceneHandler`（1 个类）
3. `ai_scene_config` 插配置行（管理端操作）
4. 业务 Service 调 `AiSceneJsonClient` + 写规则兜底

→ **4 步，且不改网关任何代码**。这是收口设计的正向验证。

**新增会话型/流式能力（收口外的世界）**：
→ 只能像面试主干那样直连，然后被建议加灰度开关、治理前置……进入 2.2 的粘合循环。

**结论：收口内的扩展成本确实被简化了；乱的感受全部来自收口外的部分。**

---

## 6. 判断与建议方向（仅为方向，不构成改动）

1. **不要回退网关**。反事实推演（§3）表明收益真实，尤其安全收口；回退只会回到 11 处散养。
2. **乱的根源是"半收口"**。短期应有意识冻结收口外的直连新增（避免再出第二个"面试主干式特例"），要么走网关，要么明确挂账。
3. **决定性技术项是网关的会话型流式**（多轮消息 + 记忆 + per-agent 模型 + SSE）。这是 D1/D2 的共同解锁钥匙，做完后可删掉灰度开关、治理前置、InterviewAgentClientImpl 的直连分支，净删代码。
4. **低成本快赢**：D3 双命名清理、D4 AiProperties 删除、D6 TODO 收尾——与架构无关的卫生债，随手可清。
5. **task 子任务（D5）**：建议接受现状或等场景数量增长后再拆——当前 3 个 task 尚可维护，过早拆配置行反而增加配置表行数。

---

## 7. 一页总结

```
感受："本来要简化，现在维护更多了"
事实：收口内（11 场景走网关）→ 确实简化，新增场景 4 步零网关改动
      收口外（面试主干/管理端对话）→ 确实更复杂，1 个特例背 5 个概念
根因：网关缺"会话型流式"能力，导致两套体系平行 + 粘合层滋生
性质：80% 的乱是过渡期债务（可消除），不是网关设计错误
方向：补会话型流式 → 合并两套体系 → 净删代码；在此之前冻结收口外新增
```
