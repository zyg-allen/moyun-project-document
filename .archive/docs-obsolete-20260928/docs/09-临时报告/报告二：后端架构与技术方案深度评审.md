# 报告二：后端架构与技术方案深度评审

> **评审对象**：moyun-server（Spring Boot 3.3.2 + Java 21）  
> **代码规模**：1,424 个 Java 源文件，194 张数据库表  
> **评审维度**：架构设计、技术选型、核心模块实现、代码质量、性能与扩展性  

---

## 一、架构总览（评分：8.0/10）

### 1.1 分层架构

项目采用经典的分层架构，基于 RuoYi-Vue 3.8.7 脚手架扩展：

```
com.moyun
├── common      # 通用模块（注解/常量/枚举/异常/过滤器）—— 无业务逻辑
├── core        # 核心框架层（AOP/配置/安全/MVC/数据源）—— 不写业务
├── system      # 系统管理（RBAC/部门/字典/日志/通知）—— 基座成熟
├── portal      # 门户业务（文章/用户/评论/面试/OJ/读书）—— 核心流量入口
├── ext         # 扩展模块
│   ├── cms     # 后台内容管理（文章/面试/简历/支付/记账/审核）
│   ├── ai      # AI 底座（知识库/工作流/Agent/RAG/聊天）
│   ├── aiapp   # AI 统一网关（场景配置/限流/熔断/执行日志/Handler）
│   ├── file    # 文件管理（MinIO/本地）
│   ├── job     # 定时任务（Quartz）
│   └── generator # 代码生成器
├── ledger      # 记账业务模块（独立包，与 portal 同级）
├── pay         # 支付业务模块（公共支付通道）
└── vip         # VIP 会员体系（v12 新增，独立包）
```

**优点**：
- 包结构语义清晰，`ext` 作为可选插拔模块的设计理念正确。
- `ai` 与 `aiapp` 分离：底层能力（langchain4j/RAG/Agent）与上层网关（治理/路由/限流）解耦。
- `ledger`、`pay`、`vip` 作为独立顶级包，避免与 `portal`/`cms` 耦合，符合领域驱动设计（DDD）包边界。

**改进点**：
- `ext` 命名略显模糊（"扩展"），`aiapp` 从 `ai2` 重命名后语义改善，但 `ext` 本身仍带有"非核心"的暗示。建议未来考虑将 `cms`、`ai`、`aiapp` 提升为与 `portal` 同级的顶级包。
- `portal` 包内混合了 Controller、Service、Judge（OJ）、Security 等多个职责，随着业务增长可能需要进一步拆分（如 `portal.interview`、`portal.article` 子包已存在，但 Judge 组件可考虑独立）。

## 二、核心模块技术方案评审

### 2.1 AI 统一网关（aiapp 包）—— 项目技术巅峰（评分：9.0/10）

**设计亮点**：

1. **五层编排架构**（`AiGatewayService.execute`）：
   - 意图判断（`IntentClassifier`）→ 语义缓存（`SemanticCache`）→ 场景路由（限流/配置合并/Agent 人设注入）→ Handler 执行（异常降级）→ 响应输出（缓存回写/日志/指标/输出过滤）。
   - 每层职责单一，可独立扩展。

2. **Handler 插件化**：
   - 11 个场景 Handler（`VoiceInterviewHandler`、`FinanceAnalysisHandler`、`ResumeOptimizeHandler` 等）继承 `AbstractAiSceneHandler`，只需实现提示词构建与结果解析。
   - `AiSceneRegistry` 自动扫描注册，新增场景零配置接入。

3. **安全三件套**：
   - **注入防护**（`PromptInjectionGuard`）：DANGEROUS 直接拒绝，SUSPECT 放行由数据隔离兜底。
   - **成本熔断**（`TokenCostGuard`）：场景日 Token 限额，超限自动降级。
   - **输出过滤**（`AiOutputFilter`）：复用 DFA 词树脱敏，不另建检测体系。

4. **降级策略**（`FallbackStrategy`）：
   - 按场景类型差异化降级（语音面试返回友好提示 / 财务分析返回空报告 / 通用场景返回静态提示）。

5. **可观测性**：
   - `AiExecuteLog` 全字段落库（requestId/userId/scene/handler/model/costYuan/status/errorCode）。
   - 管理端查询/汇总/详情/清理闭环。

**待改进**：
- 流式输出（SSE）目前由 `InterviewAgentClientImpl` 直连 langchain4j 绕过网关（v12.2 灰度开关缺省 true，保留但经网关前置检查）。建议后续将 SSE 能力纳入 `AiGatewayService`，实现全量收口。
- `SemanticCache` 基于 Redis，命中率与缓存键设计（userId + sceneCode + inputHash）在个性化场景（如面试，同一用户多次面试内容不同）下可能命中率偏低，需监控调优。

### 2.2 支付网关（pay 包）—— 设计规范，待生产落地（评分：7.5/10）

**设计亮点**：

1. **状态机清晰**：CREATED → PAID → SETTLED，条件更新防并发重复推进。
2. **幂等复用**：同 bizType+bizNo 已有未关单直接复用。
3. **事务边界**：回调业务分发放在 `TransactionTemplate` 内，任一环节失败整体回滚。
4. **渠道路由**：`List<PayChannel>` 自动注入，按 channelCode 路由，扩展新渠道只需新增 Bean。
5. **业务回调**：`List<PayCallbackHandler>` 按 bizType 路由，打赏/VIP/记账等业务解耦。

**待改进**：
- `WechatPayChannel` 当前为 mock 实现，所有方法返回模拟数据。生产接入需完成：native 下单 v3/transactions/native、查询、回调验签（NotificationParser）、关单。
- 支付回调的幂等性：需确保同一笔支付多次回调不会重复分账（当前 `PayGatewayImpl` 用条件更新 PAID → SETTLED 防重，但需验证极端并发下的正确性）。
- 缺少支付超时关单的定时任务（虽然查询/轮询时惰性关单，但无主动扫描）。

### 2.3 VIP 体系（vip 包）—— 注解驱动设计优雅（评分：8.5/10）

**设计亮点**：

1. **`@VipOnly` 注解**：`@VipOnly(platform = "portal", benefit = "voice_interview", consume = true)`，声明式权益控制。
2. **启动扫描**：`VipApiScanner` 扫描所有 `@VipOnly` 方法，自动注册到 `vip_api_registry`，后台可动态禁用接口。
3. **切面校验链**：开关关闭 → 放行（灰度）→ 注册表禁用 → 放行（运营逃生口）→ 未登录 401 → 权益校验/消耗 402。
4. **Redis 原子计数 + DB 降级**：次数消耗先扣 Redis，异步落库，保证高并发下的准确性。

**待改进**：
- `VipOnlyAspect.isDisabledInRegistry()` 使用 `AntPathMatcher` 做路径匹配，但注释提到"含 {id} pattern 直存的接口无法用 URI 命中"，存在精确匹配盲区。建议将注册表存储 pattern 化路径（如 `/portal/interview/voice/{id}/start`），而非实际 URI。

### 2.4 记账模块（ledger 包）—— 财务严谨性值得肯定（评分：8.5/10）

**设计亮点**：

1. **六类型联动矩阵**：支出/收入/转账/借款/还款/校准，单事务内完成主记录 + 联动记录（如转账同时生成转出方支出和转入方收入）。
2. **冲正重放**：更新时先查旧记录，反向冲正旧联动，再写入新联动，保证账目一致性。
3. **余额校验**：支出/转出时强制校验账户余额不足阻断（v11.70），"钱从哪来"必须有据可查。
4. **金额口径统一**：v11.31 全项目统一为元（DECIMAL(18,2) + BigDecimal），消除分/元换算隐患。
5. **AI 财务分析**：接入统一网关，evidence/expectedImpact 契约 + 快照多版本 + 异步任务化。

**待改进**：
- 分类删除校验流水绑定的实现需确认是否有 N+1 查询风险（分类数量多时应批量校验）。
- 记账 App 前端仅 37 个文件，功能相对精简，但已覆盖核心场景。

### 2.5 OJ 判题系统（portal.judge）—— 沙箱设计合理（评分：8.0/10）

- Docker 沙箱隔离，异步队列处理，支持 7 语言 ACM 模板。
- 隐藏用例防泄露（v10.16），安全设计到位。
- `JudgeAsyncWorker` 作为独立基础设施，与 AI 异步任务区分明确。

## 三、代码质量评审

### 3.1 规范遵守度（评分：7.5/10）

**优点**：
- 命名规范：大驼峰类名、小驼峰方法/变量、全大写常量，分层前缀/后缀约定（Controller/ServiceImpl/Mapper）。
- Lombok 使用规范：`@Data`、`@Slf4j`、`@RequiredArgsConstructor` 普及度高。
- OpenAPI 注解：`@Tag` + `@Operation` 覆盖率高（Knife4j 文档完整）。
- 中文注释：符合项目规范，注释质量较高（含方案文档锚点引用）。

**问题**：
- **事务注解分布**：219 个 `@Transactional`，分布较广。部分读操作也加了 `@Transactional`（可能为习惯性复制粘贴），建议只写操作加事务，读操作避免不必要的开销。
- **异常处理**：存在 4 处 `e.printStackTrace()`（`PortalLoginController`、`BeanUtils`、`ServletUtils`、`FileUploadException`），应统一改为 `log.error`。
- **System.out.println**：`MoyunApplication` 启动横幅（可接受）、`RateLimiter` 限流日志（应改为 log）、`RyTask` 定时任务（应改为 log）、`EscapeUtil` 工具类 main 方法（可接受）。
- **TODO 残留**：22 个 TODO，主要集中在：阿里云短信（3 处）、OCR 真实 API（2 处）、微信支付（5 处）、工作流性能优化（1 处）、知识库配置（2 处）、Dashboard 缓存（1 处）、真实四要素校验（2 处）。**其中支付/短信/OCR 为上线阻塞项**。

### 3.2 测试覆盖（评分：4.0/10）

- 测试文件仅 22 个，相对于 1,424 个生产代码文件，覆盖率极低（约 1.5%）。
- 现有测试集中在 AI 底座（`PromptInjectionGuardTest`、`TokenCostGuardTest`、`SceneConvergenceContractTest` 等）和面试评分引擎（`AnswerScoringEngineTest`），质量较高。
- **严重缺口**：支付网关、记账六类型联动、用户认证、文章发布等核心链路零测试。
- **建议**：上线前至少补齐支付回调、VIP 权益消耗、记账冲正、用户注册登录的单元测试和集成测试。

### 3.3 SQL 与数据库（评分：8.0/10）

**优点**：
- v12.1 将 50 个 Mapper 的 200 个内联 SQL 注解全部迁移到 XML，消除注入面。
- SQL 脚本按日期前缀幂等交付，DDL/DML 分离，增量补丁规范。
- 194 张表，结构合理，索引需进一步审查（大表如 `portal_article`、`portal_comment` 的查询性能）。

**问题**：
- 部分 XML 中动态 SQL 的 `<if>` 条件较多，需确保不会生成低效的 SQL（如全表扫描）。
- 大表分页查询建议确认是否使用 MyBatis-Plus 分页插件（`PaginationInnerInterceptor` 已引入，需验证配置）。

## 四、性能与扩展性评估

| 维度 | 评估 | 建议 |
|------|------|------|
| **数据库连接** | Druid 连接池，配置合理 | 生产环境需监控活跃连接数与等待队列 |
| **缓存策略** | Redis 用于登录态/限流/字典/语义缓存 | 建议增加业务数据缓存（如文章详情、首页聚合数据），减轻数据库压力 |
| **异步处理** | AI 任务异步化（`AiTaskService`）、OJ 判题异步化 | 建议引入消息队列（RabbitMQ/RocketMQ）替代当前基于 Redis/数据库的异步机制，提升可靠性 |
| **文件存储** | MinIO（可降级本地） | 生产必用 MinIO，本地存储不适合多实例部署 |
| **前端构建** | Vite + Rollup 手动分块 | 合理，Monaco 单独成块 |
| **并发安全** | 乐观锁（`@Version` 或条件更新）、Redis 原子操作 | 支付/VIP 等关键链路已使用，文章审核等需确认 |
