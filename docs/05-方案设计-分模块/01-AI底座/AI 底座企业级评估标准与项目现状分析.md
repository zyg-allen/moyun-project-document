> **评估依据**：`devlog.md` + 项目文档（**基于文档推断，非代码实测**，部分项需你实际核实）
> **评估日期**：2026-09-10（对应代码基线 v11.48）

## 第一部分 · 评估框架

### 1.1 评分方法

每个评估项按 5 星制打分：

| 星级    | 含义   | 对标                                |
| ----- | ---- | --------------------------------- |
| ★★★★★ | 行业领先 | 可直接对标 Dify / Coze / LangSmith 等平台 |
| ★★★★☆ | 企业可用 | 有核心能力，缺部分高级特性，生产可跑                |
| ★★★☆☆ | 基础可用 | 功能能跑，工程化不足，有隐患                    |
| ★★☆☆☆ | 原型级  | 能演示，不能上生产                         |
| ★☆☆☆☆ | 缺失   | 无实现                               |

### 1.2 评估维度（10 大项）

```
┌─────────────────────────────────────────────────────────┐
│  应用层  场景配置 · 统一网关 · 灰度 · 限流 · 缓存 · 降级   │
├─────────────────────────────────────────────────────────┤
│  编排层  Agent · 工作流 · 记忆 · 规划 · 护栏               │
├─────────────────────────────────────────────────────────┤
│  能力层  模型配置 · 工具调用 · 知识库/RAG · 提示词         │
├─────────────────────────────────────────────────────────┤
│  基础设施  向量存储 · 异步任务 · 流式输出 · 上下文管理      │
├─────────────────────────────────────────────────────────┤
│  治理层  可观测性 · 成本 · 安全 · 合规 · 测试              │
└─────────────────────────────────────────────────────────┘
```

### 1.3 LangChain4j 企业级抽象基线

项目使用 **LangChain4j 1.0.0-beta3**，企业级应充分利用其核心抽象：

| 抽象                           | 用途        | 企业级要求                    |
| ---------------------------- | --------- | ------------------------ |
| `ChatLanguageModel`          | 同步对话      | 多模型路由 + 降级               |
| `StreamingChatLanguageModel` | 流式对话      | SSE/WebSocket 输出         |
| `EmbeddingModel`             | 向量化       | 多模型可切换                   |
| `EmbeddingStore`             | 向量存储      | 可替换（ES/JVector/PgVector） |
| `ContentRetriever`           | 检索        | 混合检索 + 重排                |
| `RetrievalAugmentor`         | RAG 增强    | 查询转换 + 多路召回              |
| `AiServices`                 | 声明式 Agent | 接口 + 注解驱动                |
| `ToolSpecification`          | 工具定义      | JSON Schema              |
| `ChatMemory`                 | 会话记忆      | 窗口 + 摘要策略                |

| 子项   | 企业级标准                                                   |

| 多供应商 | 至少支持 OpenAI / 通义 / Claude / DeepSeek / 本地模型 5 类         |

### 亮点 7：数据指纹自动失效（v11.40）⭐⭐⭐⭐

`ledger_ai_analysis_report.data_fingerprint` 含 `cfg:` 段，改配置当月快照自动失效重算。**这是"缓存与配置一致性"的优雅解法**，很多团队会忘。

代码、SQL、菜单、文档四同步，在 devlog 中严格执行。**这是团队工程素养的体现**。

## 第六部分 · 需要改进的（按优先级）

### P0 · 阻断级（影响 AI 底座"能不能用"）

#### P0-1：Function Calling 工具调用体系完全缺失 ★★☆☆☆

**现状**：有 ai_tool 表，但无 Schema 定义、无执行引擎、无错误处理、无审计。

**企业级标准**：

```java
@Tool("查询用户订单")
public Order queryOrder(
    @P("订单号") String orderNo,
    @P("用户ID") Long userId
) { ... }
```

**为什么是 P0**：没有 Function Calling，Agent 就无法"自主执行任务"，只能做单轮对话。**这是"AI 应用"和"AI Agent"的分水岭**。你项目的 devlog v11.39 已经把"业务能力注册为 Agent Tool"列为 Phase 2，说明团队也认识到了。

**建议**：优先落地 LangChain4j 的 `@Tool` 注解 + `ToolSpecification`，把 3~5 个高频业务能力（记账查询/题库检索/文章搜索）注册为工具，跑通一个端到端 Demo。

---

#### P0-2：Prompt 注入防护完全缺失 ★☆☆☆☆

**现状**：无输入清洗、无指令隔离、无越狱检测。

**企业级标准**：

- 输入层：清洗特殊字符、检测注入模式
- 指令层：system prompt 用分隔符隔离用户输入
- 输出层：过滤敏感内容

**为什么是 P0**：LLM 应用的头号安全风险。用户可以通过"忽略以上指令"绕过你的 system prompt，让 AI 泄露敏感数据或执行危险操作。**你的项目有支付、有实名认证，一旦被注入后果严重**。

**建议**：至少在网关层加输入清洗 + 系统提示词用 `### 用户输入 ###` 包裹。

---

#### P0-3：AI 网关场景迁移未完成 🔶

**现状**：7 个场景注册，仅 finance_analysis 接入，voice_interview / resume_parse / resume_optimize / question_generate 待迁移。

**为什么是 P0**：这是 Phase 1 的核心任务，也是"配置驱动"能否兑现的关键。**设计再优秀，不落地就是零**。

**建议**：按 devlog 计划逐个迁移，每个场景迁移后跑通端到端。

---

#### P0-4：成本监控与熔断缺失 ★☆☆☆☆

**现状**：有 Token 统计，但无成本换算、无预算告警、无熔断。

**为什么是 P0**：一个被注入的用户或一个死循环 Agent，可能一夜烧掉几千元 Token。**这是创业团队最容易忽视但后果最严重的风险**。

**建议**：

- ai_scene_config 加 `daily_token_limit` 字段
- 网关层统计用户日 Token 消耗，超限拒绝
- ai_execute_log 加成本字段，管理页展示

### P1 · 重要级（影响 AI 底座"好不好用"）

#### P1-1：Agent 规划能力缺失 ★☆☆☆☆

3. **未覆盖业务逻辑**：仅评估 AI 底座，不含业务功能完整性

### A.2 建议的验证动作

| 待核实项    | 验证方法                                        |
| ------- | ------------------------------------------- |
| 密钥是否加密  | 查 `ai_model_config` 表 api_key 字段是否密文        |
| 工具注册实现  | 查 `ai_tool` 表 + 是否有 ToolRegistry 类          |
| 工作流节点类型 | 查 WorkflowEngine 支持的节点枚举                    |
| 语义缓存    | 查 SemanticCache 是否有实际检索逻辑                   |
| 意图识别    | 查 AiGatewayController 是否调用 IntentClassifier |
| 限流是否生效  | 查 @RateLimiter 注解在网关是否生效                    |
| 输出过滤    | 查是否有 OutputFilter 类                         |
| 成本统计    | 查 ai_execute_log 是否有 cost 字段                |

### A.3 一句话总结

> **你的 AI 底座是一座"设计精良但未完工的大厦"——地基（场景注册/配置驱动/异步任务/流式输出）已达国内中厂水准，但上层建筑（Function Calling/Agent 规划/语义缓存/安全防护）还停留在图纸阶段。当务之急是把 Phase 1 的网关迁移 + 工具调用落地，让"配置驱动"从设计变成现实。**
