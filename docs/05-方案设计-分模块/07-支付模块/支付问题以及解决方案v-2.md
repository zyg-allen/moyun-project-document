# 出现"两套钱包"的不合理做法





你这个质疑非常对，而且你描述的模式**才是正规的资金架构**。先说结论：

**你现在的"双钱包并存"确实不合理，是历史遗留的设计债；你描述的"公账账户 A + 分账记账"模式，才是合规且正确的做法。**

---

## 一、为什么会出现"两套钱包"

从你的 devlog 看，这是**两个功能各自独立演进的产物**：

| 时间        | 功能     | 表                  | 目的      |
| --------- | ------ | ------------------ | ------- |
| v5.0      | 打赏 MVP | 早期积分/打赏表           | 用积分替代真钱 |
| v11.0     | 支付网关   | `pay_user_account` | 真钱打赏分账  |
| v9.0/v9.5 | 社区钱包   | `cms/wallet` 相关    | 充值/消费   |

**问题根源**：打赏功能和钱包功能是**两拨人（或两个时期）分别做的**，各建各的表，没有统一。

**结果**：

- 社区钱包：用户充值进去，平台内消费
- 打赏钱包：打赏所得，用户提现
- **两套余额、两套流水、两套对账逻辑**

这在实际运营中会出大问题——**同一个用户，他的钱到底在哪？总余额是多少？**

---

## 二、你的"公账账户 A"模式对不对

**完全正确。** 这是支付行业的**标准做法**，专业叫法是：

- **平台收款账户**（你的"公账 A"）
- **分账/记账系统**（你描述的"数据记录分账"）
- **结算/提现**（你描述的"从 A 转出到 B/C/D"）

### 正规的资金流

```
用户支付 100 元
    ↓
全部进入平台公账账户 A（微信商户号/支付宝商户号）
    ↓
平台内部记账（不动真钱，只记账）：
    ├── 用户 B 的虚拟余额 +90
    └── 平台抽成 +10
    ↓
（此时真钱 100 元都躺在 A 里）
    ↓
用户 B 申请提现 90 元
    ↓
从 A 账户转账 90 元到 B 的银行卡
    ↓
记账：B 的虚拟余额 -90
```

### 关键点

| 要点         | 说明                          |
| ---------- | --------------------------- |
| **真钱集中**   | 所有真钱都在 A（商户号），不分散           |
| **虚拟余额**   | 用户看到的"钱包余额"是**记账数字**，不是真钱   |
| **分账是记账**  | 平台抽成、用户所得，都是数据库记录，不是真的转账    |
| **提现才动真钱** | 只有提现时，才从 A 转出到用户银行卡         |
| **对账核心**   | A 的余额 = 所有用户虚拟余额 + 平台抽成（守恒） |

## 三、你现在的问题在哪

对照你的项目：

### 问题 1：双钱包不统一

| 现状          | 问题         |
| ----------- | ---------- |
| 社区钱包（充值/消费） | 独立余额       |
| 打赏钱包（分账所得）  | 独立余额       |
| **用户有两个余额** | 用户困惑，运营难对账 |

**正确做法**：**一个用户，一个钱包，一个余额**。充值和打赏所得都进同一个余额。

### 问题 2：真钱与虚拟余额的关系不清晰

你的 devlog v11.0 提到：

> "分账（业内成熟做法：复式记账）"
> "每笔支付成功拆两条流水：平台抽成 + 用户所得"

**这个方向是对的**，但需要确认：

- 真钱是否真的都进了**一个**商户号？
- 用户虚拟余额的**总和**是否等于商户号余额（扣除已提现）？
- 提现时是否从商户号真实转出？

如果这些都成立，那你的架构其实**已经接近正确**，只是**双钱包**这一层是多余的。

### 问题 3：微信支付的合规要求

微信支付（尤其是**电商收付通**或**分账**功能）对资金有明确要求：

| 要求       | 说明                          |
| -------- | --------------------------- |
| **资金归集** | 用户支付的钱必须进平台商户号              |
| **分账**   | 平台可设置分账比例，但资金仍在商户号          |
| **提现**   | 用户提现时从商户号转出                 |
| **二清风险** | 平台不能"代收代付"（即用户钱不进商户号，平台自己转） |

**你的模式如果实现正确，是合规的。**

## 四、正确的架构应该长什么样

### 推荐架构（单钱包 + 公账 + 分账记账）

```
┌─────────────────────────────────────────────┐
│  用户侧（门户/App）                          │
│  ┌─────────────────────────────────────┐   │
│  │  统一钱包（一个余额）                │   │
│  │  ├── 充值余额                        │   │
│  │  ├── 打赏所得                        │   │
│  │  ├── 消费支出                        │   │
│  │  └── 提现记录                        │   │
│  └─────────────────────────────────────┘   │
└─────────────────────────────────────────────┘
                    ↓ 记账
┌─────────────────────────────────────────────┐
│  平台记账层（数据库，不动真钱）              │
│  ├── pay_user_account（用户虚拟余额）        │
│  ├── pay_ledger_entry（流水明细）            │
│  └── 分账记录（平台抽成 + 用户所得）         │
└─────────────────────────────────────────────┘
                    ↓ 真实资金
┌─────────────────────────────────────────────┐
│  公账账户 A（微信商户号/支付宝商户号）       │
│  ├── 所有用户支付的钱都在这                  │
│  ├── 提现时从这里转出                        │
│  └── 余额 = 所有用户虚拟余额 + 平台抽成      │
└─────────────────────────────────────────────┘
                    ↓ 提现
┌─────────────────────────────────────────────┐
│  目标账户 B/C/D（用户银行卡）                │
└─────────────────────────────────────────────┘
```

### 核心原则

| 原则           | 说明                    |
| ------------ | --------------------- |
| **一个用户一个钱包** | 不分社区钱包/打赏钱包           |
| **真钱集中**     | 所有真钱在商户号 A            |
| **虚拟余额是记账**  | 用户看到的是数字，不是真钱         |
| **提现才动真钱**   | 从 A 转出到用户银行卡          |
| **守恒校验**     | A 余额 = Σ用户虚拟余额 + 平台抽成 |
| **流水可追溯**    | 每笔钱都有来源和去向            |

## 五、你该怎么改

### 短期（不建议大改）

如果双钱包已经上线且有用户，**不建议现在推倒重来**，可以：

1. **统一展示**：在用户端把两个钱包余额**合并显示**为"总余额"
2. **统一提现**：提现时从两个钱包合并计算
3. **对账工具**：后台提供"用户总余额 = 社区钱包 + 打赏钱包"的对账视图

### 长期（推荐重构）

如果还在开发阶段（你说还没部署），**建议现在就统一**：

1. **合并为单钱包**：`pay_user_account` 作为唯一钱包表
2. **充值/打赏所得都进这个钱包**
3. **消费/提现都从这个钱包出**
4. **社区钱包表废弃或作为历史数据迁移**
5. **真钱全部走商户号，记账在数据库**

### 关键验证

重构后必须能回答：

- [ ] 用户 A 的总余额是多少？（一个数字）
- [ ] 平台商户号余额 = Σ所有用户余额 + 平台抽成？（守恒）
- [ ] 用户提现时，钱从哪出？（商户号 A）
- [ ] 每笔打赏，用户实得多少、平台抽成多少？（分账记录）

## 六、微信支付的具体要求（补充）

如果你要接真实微信支付，需要注意：

| 模式        | 说明                 | 适用    |
| --------- | ------------------ | ----- |
| **普通商户**  | 用户支付进你的商户号，你提现到银行卡 | 简单场景  |
| **服务商**   | 你作为服务商，帮子商户收款      | 多商户平台 |
| **电商收付通** | 平台归集资金，分账给商户       | 电商平台  |
| **分账**    | 支付时设置分账比例          | 打赏/分销 |

**你的打赏场景**，如果用户是个人（不是商户），**普通商户 + 提现**就够了；如果用户是创作者需要分账，**分账功能**更合适。

**关键合规点**：

- 用户支付的钱**必须进你的商户号**（不能进个人账户）
- 提现**必须从商户号转出**（不能平台自己转账）
- 不能"二清"（即平台代收代付、资金不过商户号）

### 8.3 账户模型分类与新场景接入规范（v11.80 固化，后续场景照此判断）

**原则：先分清资金流，再选分账方法；各场景业务表、bizType、回调处理器均独立实现，只共用底层通道与记账表。**

| 分类 | 资金流 | 分账方法 | 流水分录 | 用户钱包 | 已接入场景 | 规划中 |
|---|---|---|---|---|---|---|
| **平台直收类** | 用户 → 平台公账（全额，无第三方收款人） | `settlePlatform` | PLATFORM/credit 单分录 | 不涉及 | 记账App打赏（ledger_tip）、记账VIP订阅（ledger_vip）、面试会员订阅（interview_vip）、简历优化会员订阅（resume_optimize） | — |
| **分账类** | 用户 → 收款人，平台抽成 | `settle` | PLATFORM/credit 抽成 + USER/credit 收款人所得 双分录 | 收款人余额入账（可提现） | 门户文章打赏/付费阅读（tip） | 专栏、课程 |
| **提现出金** | 用户余额 → 银行卡 | `WithdrawOrder` | USER/debit | 余额原子扣减 | 提现（withdraw） | — |

**新场景接入三步**：
1. 判断收款模式：有没有第三方收款人？有 → 分账类；无 → 平台直收类
2. 建独立业务表 + 独立 bizType（枚举注册）+ 独立 CallbackHandler（bizType() 返回值路由）
3. 回调事务内按分类调 `settle` / `settlePlatform`（+ 站内通知），公账守恒自动成立：
   平台直收 = 平台所得全额；分账类 = 抽成归平台 + 余款进收款人余额

**守恒公式（收银台收入侧）**：平台所得（PLATFORM/credit 合计）+ 用户钱包余额（ΣUSER/credit -
Σ提现）= 全部成功支付金额（GMV 口径按业务订单统计，pay_order 通道单据不重复计入）。

**收入口径更新**：平台所得 = 公共通道 PLATFORM/credit 分录合计（含 App 打赏全额 + 门户抽成，
分录为准不双算）；用户所得 = USER/credit 分录合计。

**SQL**：`20260914-06-ledger-tip-channel.sql`（client_uuid 幂等 + uk_client_uuid 唯一索引 + paid_time +
存量演示单彻底删除——测试数据不保留）。
