# 邀请注册与协作使用 · 设计方案 V1.0

> 场景：张三有个合伙仓库，想把李四拉进来一起卖货。
> 李四**可能还没注册**，也可能已经是用户。

---

## 一、核心设计原则

| 原则 | 说明 |
|---|---|
| **一个链接搞定** | 分享出去，对方点开就知道"谁邀请我去哪" |
| **注册即加入** | 新用户注册完**直接进那个仓库**，不是丢到空白首页 |
| **老用户零摩擦** | 已登录的点开链接，确认一下就直接加入 |
| **码可复用** | 一个码可以邀请多个人（合伙场景本来就不止两人） |

---

## 二、邀请码模型（一张表两用）

```sql
ledger_invite
  id            bigint PK
  code          varchar(16)  邀请码，唯一，如 A7K2M9
  type          varchar(20)  warehouse=加入仓库 / register=纯拉新
  warehouse_id  bigint       目标仓库（type=warehouse 时必有）
  role          varchar(20)  加入后的角色：member / viewer
  created_by    bigint       邀请人
  expire_at     datetime     过期时间（默认 7 天）
  max_use       int          可用次数上限（默认 10）
  used_count    int          已使用次数
  status        tinyint      1 有效 / 0 已撤销
  UNIQUE KEY uk_code (code)
```

**为什么不做「一次性码」**：合伙卖货天然是多人，一码多人更实用。
**为什么保留了 `max_use`**：防止码被转发到群里被陌生人加进来。

## 三、全链路流程

### 3.1 邀请方（张三）

```
仓库设置 → 成员 → [＋ 邀请]
        ↓
选择角色（可出入库 / 只读）
        ↓
生成码 A7K2M9，显示：
   ┌────────────────────────────┐
   │  邀请一起管理「小商店」      │
   │                            │
   │      A7K2M9                │
   │   7 天内有效 · 还可加 10 人  │
   │                            │
   │  [复制链接]  [生成二维码]    │
   └────────────────────────────┘
```

分享链接格式：

```
H5    : https://host/#/pages/invite/index?code=A7K2M9
小程序 : /pages/invite/index?code=A7K2M9
```

### 3.2 被邀请方（李四）

```
点开链接 → /pages/invite/index?code=A7K2M9
        ↓
   调 GET /portal/invite/{code} 校验
        ↓
   ┌── 未登录 ──────────────────┐
   │ 张三 邀请你一起管理          │
   │       「小商店」仓库         │
   │                            │
   │  [ 手机号登录 ]  [ 注册并加入 ] │
   └────────────────────────────┘
        ↓ 注册
   手机号 + 验证码 + 密码
        ↓
   注册成功 → 自动调「加入仓库」
        ↓
   跳转 /pages/warehouse/index，并 toast「已加入小商店」
```

```
   ┌── 已登录 ──────────────────┐
   │ 张三 邀请你一起管理          │
   │       「小商店」仓库         │
   │                            │
   │  [ 加入 ]   [ 暂不 ]         │
   └────────────────────────────┘
```

### 3.3 加入成功后

| 项 | 表现 |
|---|---|
| 仓库列表 | 多出「小商店」，徽标显示仓库性质 |
| 可见范围 | 货架 / 商品 / 库存 / 流水全可见 |
| 可操作 | 出入库 / 移库 / 盘点 |
| 不可操作 | 改仓库设置 / 删仓库 / 管成员 |
| 流水 | 显示「谁卖的」（`operator_id`） |

## 四、接口设计

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/portal/ledger/invites` | 生成邀请码（仅 owner） |
| GET | `/portal/invite/{code}` | **校验码**（免登录可调，返回仓库名 + 邀请人昵称） |
| POST | `/portal/invite/{code}/accept` | 接受邀请（需登录） |
| DELETE | `/portal/ledger/invites/{id}` | 撤销 |
| GET | `/portal/ledger/invites?warehouseId=` | 该仓库的有效邀请列表 |

**`GET /portal/invite/{code}` 必须免登录** —— 否则未注册用户看不到"谁邀请我"。

## 五、注册流程复用

已有能力，不重造：

```
POST /portal/sendSmsCode   发送验证码（已有）
POST /portal/register      手机号注册（已有，之前修过路径）
```

**注册成功后需要拿到 token** → 再调 `accept`。

## 六、安全与边界

| 风险 | 对策 |
|---|---|
| 码被转发滥加 | `max_use` + `expire_at` + owner 可撤销 |
| 码被暴力猜 | 6 位 base32（去易混字符），足够 |
| 加错仓库 | 校验码时显示仓库名，让用户确认 |
| 重复加入 | `accept` 幂等：已在仓库直接返回成功 |
| 自己加自己 | 拒绝 |
| 邀请链接被爬 | 链接本身不含敏感信息，只有码 |

## 九、和「直接在成员页填手机号」的关系

我刚做的 `POST .../members` 是**直接按手机号加人**，适合"对方已经是我好友、我知道他手机号"。

邀请码适合"发到群里 / 发给不确定手机号的人"。

**两者并存，不冲突**：

```
知道手机号 → 成员页直接加（快）
不知道 / 群发 → 生成邀请链接（广）
```

---

## 十、一个必须注意的体验点

**注册后不能只给个空白首页。**

必须：
1. 自动加入仓库
2. 直接跳到该仓库页
3. 顶部 toast「已加入『小商店』仓库，张三邀请你一起管理」

否则新用户会不知道发生了什么，这是拉新转化的关键一步。
