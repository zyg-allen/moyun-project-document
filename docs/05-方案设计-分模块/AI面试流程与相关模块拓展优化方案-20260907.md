## 一、背景与目标

### 1.1 项目现状

当前平台已具备以下能力：

- 简历模块：在线编辑（结构化字段：姓名、性别、出生日期、电话、邮箱、求职意向、教育背景、工作经历、项目经历、专业技能、自我评价）+ 附件解析（PDF/Word 文本抽取）
- 题库模块：选择题 + 编程题 + 面经，支持难度分级和分类管理
- AI 能力：LangChain4j + 通义大模型 + 知识库 RAG + 工作流 + Agent
- 面试模块：AI 模拟面试（已有基础版，直接出题模式）

### 1.2 存在的问题

| 序号  | 问题分类  | 具体问题                             | 严重度  |
| --- | ----- | -------------------------------- | ---- |
| 1   | 简历数据  | 在线编辑为结构化字段，附件解析为非结构化文本，AI 无法统一使用 | 🔴 高 |
| 2   | 面试流程  | 当前直接出题，缺少“自我介绍”环节，与真实面试场景脱节      | 🔴 高 |
| 3   | 出题逻辑  | 硬编码出题，没有利用岗位模板和简历内容的智能匹配         | 🟠 中 |
| 4   | AI 评分 | 依赖 LLM 自由发挥，缺少结构化评分标准，容易产生幻觉     | 🔴 高 |
| 5   | 业务耦合  | 业务场景与 AI 能力强耦合，改配置要改代码           | 🟠 中 |

### 1.3 目标

| 目标            | 说明                                  |
| ------------- | ----------------------------------- |
| **统一简历上下文**   | 无论从哪来，最终输出统一的 ResumeContext，供 AI 使用 |
| **真实面试流程**    | 增加自我介绍环节，6 阶段完整模拟真实面试               |
| **智能出题**      | 基于岗位 + 简历 + 薄弱点 + 随机，自动生成题单         |
| **结构化 AI 评分** | 自我介绍 + 技术问答 双维度评分，杜绝 LLM 幻觉         |
| **AI 能力解耦**   | 场景配置中心，业务只认场景代码，不直接依赖具体 AI 组件       |

## 三、核心功能设计

### 3.1 简历统一上下文（ResumeContext）

#### 3.1.1 现状与问题

**现状**：

- 在线编辑简历：数据以结构化字段存储在 `portal_user_resume` 表中（`name`、`gender`、`birth_date`、`phone`、`email`、`job_intention` JSON、`educations` JSON、`works` JSON、`projects` JSON、`skills` JSON、`self_intro` TEXT）
- 附件上传简历：通过 `ResumeParseService` 解析 PDF/Word 文档，提取纯文本后存储到 `portal_user_resume` 表的对应字段中

**问题**：

1. 在线编辑简历是结构化数据，附件解析后也是结构化数据，但两者在代码中没有统一的访问入口
2. AI 面试时需要从简历中提取信息（姓名、技能、项目经历等），但每次都要从不同位置获取，逻辑分散
3. 附件解析结果缺少来源标记（置信度、原始文件信息），无法判断数据可靠性
4. 简历摘要（给 AI 的上下文）每次都要重新拼接，没有缓存

#### 3.1.2 解决方案

**修改原因**：统一简历数据访问入口，让 AI 面试、简历优化、出题器等场景都使用同一份数据，避免重复解析和逻辑分散。

**解决问题**：

1. 简历数据来源统一（在线编辑 + 附件解析 → ResumeContext）
2. AI 面试只需要对接 ResumeContext，不需要关心简历来源
3. 附件解析置信度可追溯，低置信度数据标记人工复核
4. 简历摘要缓存，减少重复计算

#### 3.1.3 数据结构

> **字段说明**：标注 ✅ 的字段在现有 `PortalUserResume` 实体中已存在，可直接映射；标注 🆕 的字段需要新增或从解析结果中提取。

```java
public class ResumeContext {
    // ===== 个人信息 =====
    private String name;              // ✅ 已有：PortalUserResume.name
    private String gender;            // ✅ 已有：PortalUserResume.gender
    private String birthDate;         // ✅ 已有：PortalUserResume.birthDate
    private String phone;             // ✅ 已有：PortalUserResume.phone
    private String email;             // ✅ 已有：PortalUserResume.email

    // ===== 求职意向 =====
    private JobIntention jobIntention;  // ✅ 已有：PortalUserResume.jobIntention (JSON字段)
    // JobIntention 内部字段：position, city, salaryMin, salaryMax, jobType, availableTime

    // ===== 教育背景 =====
    private List<Education> educations;  // ✅ 已有：PortalUserResume.educations (JSON字段)
    // Education 字段：school, major, degree, startDate, endDate, description

    // ===== 工作经历 =====
    private List<WorkExperience> works;  // ✅ 已有：PortalUserResume.works (JSON字段)
    // WorkExperience 字段：company, position, startDate, endDate, description

    // ===== 项目经历 =====
    private List<Project> projects;      // ✅ 已有：PortalUserResume.projects (JSON字段)
    // Project 字段：name, role, startDate, endDate, description, url

    // ===== 技能 =====
    private List<Skill> skills;          // ✅ 已有：PortalUserResume.skills (JSON字段)
    // Skill 字段：name, level

    // ===== 自我评价 =====
    private String selfIntro;            // ✅ 已有：PortalUserResume.selfIntro

    // ===== 来源标记（🆕 新增字段） =====
    private String sourceType;           // 🆕 "online" | "attachment"
    private Integer parseConfidence;     // 🆕 解析置信度 0-100
    private String sourceFileUrl;        // 🆕 附件来源URL
    private String sourceFileName;       // 🆕 附件原始文件名
}
```

### 3.2 智能出题器

#### 3.2.1 现状与问题

**现状**：

- 现有 `pickQuestionsByProfile` 方法只有三路：薄弱点(最多3题) + 岗位必备(最多2题) + 随机兜底
- 没有“简历40%”和“薄弱点20%”的精确配比
- 出题逻辑散落在各个 Service 中，没有统一入口

**问题**：

1. 出题配比与方案设计不一致，40% 的简历题源形同虚设
2. 没有从简历项目中提取关键词匹配题库
3. 题单生成不可配置，改权重需要改代码
4. 没有考虑题目的难度递进（简单→中等→困难）

#### 3.2.2 解决方案

**修改原因**：让出题逻辑可配置、可追溯，基于岗位要求 + 简历内容 + 用户薄弱点智能生成题单，提升面试针对性。

**解决问题**：

1. 出题权重可后台配置（40%/30%/20%/10%）
2. 从简历项目中提取技术栈关键词匹配题库
3. 题目按难度递进排列
4. 题源不足时自动降级到其他类型

#### 3.2.3 出题矩阵

| 题源    | 权重  | 匹配逻辑                  | 数据来源                                                 |
| ----- | --- | --------------------- | ---------------------------------------------------- |
| 岗位核心题 | 40% | 从岗位关联的题库中按难度递进选取      | `portal_interview_question` 关联 `portal_job_template` |
| 简历深挖题 | 30% | 从简历中提取项目/技能关键词 → 匹配题库 | `ResumeContext.projects/skills`                      |
| 薄弱点题  | 20% | 从错题本/历史面试中取薄弱点 → 匹配题库 | `portal_wrong_question`                              |
| 随机兜底题 | 10% | 随机抽题，保持新鲜感            | `portal_interview_question`                          |

#### 3.2.4 题单生成示例（5题）

| 顺序  | 类型   | 难度  | 来源   | 匹配逻辑             |
| --- | ---- | --- | ---- | ---------------- |
| 第1题 | 岗位核心 | 简单  | 岗位题库 | 岗位关联题目中选最简单的     |
| 第2题 | 简历深挖 | 中等  | 项目经历 | 提取项目描述中的技术栈关键词匹配 |
| 第3题 | 岗位核心 | 中等  | 岗位题库 | 岗位关联题目中选中等难度     |
| 第4题 | 薄弱点  | 中等  | 错题本  | 从错题本中取错误次数最多的标签  |
| 第5题 | 综合   | 困难  | 系统设计 | 从岗位关联题目中选最难的     |

### 3.3 AI 面试完整流程（6阶段）

#### 3.3.1 现状与问题

**现状**：

- 当前面试流程：开始 → 直接出题 → 回答 → 评分 → 下一题 → 结束
- 没有“自我介绍”环节，没有“候选人反问”环节
- 追问逻辑简单，没有根据回答质量动态调整

**问题**：

1. 与真实面试场景严重脱节（真实面试从来都是先自我介绍）
2. 缺少自我介绍评分，无法评估候选人的沟通表达和自我认知
3. 缺少候选人反问环节，无法评估候选人的主动性和岗位匹配度
4. 追问逻辑不精细，无法模拟真实面试官的深挖行为

#### 3.3.2 解决方案

**修改原因**：让 AI 面试更接近真实面试场景，6 阶段完整模拟，提升面试真实感和有效性。

**解决问题**：

1. 增加自我介绍环节，独立评分
2. 增加自我介绍追问，验证简历真实性
3. 增加候选人反问环节，评估主动性
4. 追问逻辑细化（回答不完整→追问；回答优秀→深挖）

#### 3.3.3 面试阶段定义

| 阶段      | 内容       | 评分     | 说明                  |
| ------- | -------- | ------ | ------------------- |
| **阶段1** | 自我介绍     | ✅ 独立评分 | 逻辑结构、自我认知、岗位匹配、表达流畅 |
| **阶段2** | 自我介绍追问   | ✅      | 根据自述内容智能生成追问        |
| **阶段3** | 基础技术题    | ✅      | 按题库出题（八股文、基础知识）     |
| **阶段4** | 项目深挖     | ✅      | 按题库出题（真实项目细节、技术难点）  |
| **阶段5** | 系统设计/场景题 | ✅      | 按题库出题（开放性问题、设计方案）   |
| **阶段6** | 候选人反问    | ✅      | 考察主动性、岗位匹配度         |

### 3.4 AI 评分体系

#### 3.4.1 现状与问题

**现状**：

- 现有评分依赖 `MockInterviewServiceImpl.scoreAnswer` 规则打分（关键词命中率 + 结构完整性 + 长度档位）
- LLM 评分（`ResumeAiAdviceService`）用于简历优化建议，不用于面试评分
- 评分维度固定，不可配置

**问题**：

1. 规则评分只能做基础判断，无法理解语义深度
2. LLM 评分没有结构化约束，容易产生幻觉
3. 评分维度不可配置，无法针对不同岗位调整权重
4. 评分结果不可解释，用户不知道“为什么得这个分”

#### 3.4.2 解决方案

**修改原因**：结合 LLM 语义理解能力 + 规则引擎的确定性，实现可解释、可配置的结构化评分。

**解决问题**：

1. LLM 做语义分析（70%权重），规则引擎做交叉验证（30%权重）
2. 评分维度可后台配置（权重可调）
3. 防幻觉机制：分数范围校验 + 一致性校验 + 双模型交叉验证
4. 评分明细可追溯，每项得分都有依据

#### 3.4.3 评分方式

| 方式           | 适用场景             | 权重  | 说明              |
| ------------ | ---------------- | --- | --------------- |
| **LLM 分析评分** | 主观题、自我介绍、项目描述    | 70% | 大模型语义理解，多维打分    |
| **规则引擎校验**   | 关键词命中、回答长度、结构化检测 | 30% | 防止 LLM 幻觉，做交叉验证 |

#### 3.4.4 综合评分算法

```
综合评分 = 自我介绍分 × 20% + 技术面平均分 × 80%

自我介绍分 = 逻辑结构 + 自我认知 + 岗位匹配 + 表达流畅度
技术面平均分 = Σ(每题得分) / 题目总数
每题得分 = LLM分 × 70% + 规则分 × 30%
```

#### 3.4.5 防幻觉机制

| 规则          | 说明                          | 实现方式     |
| ----------- | --------------------------- | -------- |
| **分数范围校验**  | 各维度分数必须在 0-100 之间，超出则截断     | 代码层校验    |
| **总分校验**    | 各维度加权总和必须在 0-100 之间         | 代码层校验    |
| **一致性校验**   | 评语与分数必须匹配（高分不能配差评）          | LLM 二次确认 |
| **字数校验**    | 字数太少（<30字）自动扣分              | 规则引擎     |
| **关键词校验**   | 完全没有关键词命中 → 降级评分            | 规则引擎     |
| **双模型交叉验证** | 主模型与备用模型评分偏差 > 20分 → 标记人工复核 | 模型层      |

### 3.5 AI 能力配置中心

#### 3.5.1 现状与问题

**现状**：

- 现有 `ai_agent` 表已支持 Agent 定义，包含 `model_id`、`system_prompt`、`tools`、`knowledge_base_ids`、`workflow_id`
- 业务层（面试、简历优化）直接调用具体的 Agent 或模型，代码中硬编码了 `agentId` 或 `modelId`
- 场景配置散落在各个 Service 中，没有统一管理

**问题**：

1. 业务与 AI 能力强耦合，更换模型需要改代码
2. 无法做灰度/AB 测试（同一场景用不同模型）
3. 新场景接入需要重复配置，没有复用机制
4. 配置变更需要重新部署

#### 3.5.2 解决方案

**修改原因**：通过场景配置中心实现业务与 AI 能力的解耦，让配置可动态调整，无需重启服务。

**解决问题**：

1. 业务只认场景代码（如 `interview`），不关心具体用哪个模型
2. 支持灰度发布（同一场景多版本配置按权重分配流量）
3. 配置变更实时生效，无需重启
4. 新场景接入只需新增配置，无需改代码

#### 3.5.3 设计思路

```
业务场景（消费方）                    AI 能力（提供方）
┌─────────────────────┐            ┌─────────────────────────────────┐
│ AI 面试              │────配置────│ Agent（综合容器）                │
├─────────────────────┤            │  ├── 模型：GPT-4 / 通义 / Claude │
│ 简历优化             │────配置────│  ├── 知识库：RAG 检索             │
├─────────────────────┤            │  ├── 工作流：多步骤编排           │
│ 出题生成             │────配置────│  └── 工具：自定义工具调用         │
└─────────────────────┘            └─────────────────────────────────┘
```

#### 3.5.4 配置优先级

```
场景配置
    │
    ├── 有 Agent → 使用 Agent 绑定的模型/知识库/工具/工作流
    │
    └── 无 Agent → 使用手动绑定的模型/知识库/工具/工作流
```

#### 3.5.5 切换策略（灰度/AB测试）

### 3.6 面试报告增强

#### 3.6.1 现状与问题

**现状**：

- 现有面试报告包含：综合评分、各维度评分条、QA 明细列表
- 评分维度固定（回答相关性/专业度/表达流畅度/面试互动性/自信度）
- 报告没有区分自我介绍和技术问答

**问题**：

1. 自我介绍环节没有独立评分，无法评估候选人的沟通表达
2. 报告缺少“强项/弱项”分析，用户不知道改进方向
3. 没有错题自动入库，用户需要手动添加
4. 报告不可导出（PDF）

#### 3.6.2 解决方案

**修改原因**：让面试报告更全面、更有价值，帮助用户识别强项和弱项，形成“面试→错题→学习”的闭环。

**解决问题**：

1. 自我介绍独立评分模块
2. 强项/弱项自动分析（基于各维度得分）
3. 错题自动入库（得分低于60分的题目）
4. 报告导出 PDF

## 九、风险与应对

| 风险       | 可能性 | 影响       | 应对措施                           |
| -------- | --- | -------- | ------------------------------ |
| LLM 评分幻觉 | 中   | 评分不准确    | 规则引擎交叉验证 + 双模型校验 + 人工复核标记      |
| 附件解析失败   | 中   | 无法使用附件简历 | 提供手动编辑入口 + 明确错误提示              |
| 智能出题无结果  | 低   | 题单为空     | 多层降级策略（岗位→简历→随机兜底）             |
| 配置中心复杂度  | 低   | 使用成本高    | 提供默认配置 + 使用模板 + 详细文档           |
| 性能延迟     | 中   | 用户体验差    | 缓存 ResumeContext + 异步处理 + 流式输出 |

## 十、总结

| 核心改进              | 解决的问题                 | 涉及的新增/修改            |
| ----------------- | --------------------- | ------------------- |
| **ResumeContext** | 简历数据来源不统一，AI 无法使用统一格式 | 🆕 新增 5 个字段 + 新增缓存表 |
| **智能出题器**         | 出题逻辑硬编码，没有利用岗位和简历     | 🆕 新增岗位模板表 + 出题服务   |
| **自我介绍环节**        | 与真实面试场景脱节             | 🆕 新增面试配置表 + 评分维度   |
| **结构化评分**         | LLM 自由发挥，评分不可控        | 改造评分服务 + 规则引擎       |
| **AI 能力配置中心**     | 业务与 AI 能力强耦合，改配置要改代码  | 🆕 新增场景配置表 + 配置服务   |

> **一句话总结：通过 ResumeContext 统一简历数据，通过智能出题器实现岗位+简历匹配，通过6阶段流程模拟真实面试，通过结构化评分保证评分可解释，通过场景配置中心实现业务与AI能力解耦。**
