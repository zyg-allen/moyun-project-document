# 题库与学习中心模块综合评审与优化方案（5W2H）

> 评审日期：2026-08-30
> 评审范围：学习中心题库（三种练习模式）、面试题库、OJ 判题、学习行为记录、成长时间线、题库作为 AI 面试数据底座
> 评审方法：代码现状（moyun-portal / moyun-admin-vue / moyun-server）+ 设计文档（题库模块重构方案-20260820、栏目重构设计-20260819、AI语音面试官评估与落地计划等）+ 5W2H 框架

## 0. 评审结论速览

**一句话结论：设计方向是对的（统一题库 + 双维度 + 成长记录），但落地只走了三分之一——三种模式只有"选择题"一条链路是完整的，编程题判题与成长记录断链，阅读模式没有行为记录，前后台对两个维度的使用互相矛盾。当前最需要的不是加功能，而是收口。**

| 维度 | 现状评分 | 一句话诊断 |
|------|---------|-----------|
| 数据模型 | ★★★★☆ | question_type × practice_mode 双维度设计合理，业内有先例，但数据只填了一种组合，正交塌缩 |
| 选择题链路 | ★★★★☆ | 列表→做题→服务端判分→解析→成长事件，闭环基本完整 |
| 编程题链路 | ★★★☆☆ | 列表→做题→OJ 判题→提交记录完整，但**判题结果不写成长事件**，与 submitAnswer 双轨并行 |
| 阅读链路 | ★★☆☆☆ | 详情页纯阅读可用，但**无任何行为记录**（无 read 事件、无时长、无统计） |
| 代码质量 | ★★☆☆☆ | 三个列表页复制粘贴、映射重复定义、跳转规则三处三个样 |
| AI 数据底座 | ★★★☆☆ | 出题四路设计已有文档，但 knowledge_tags 无受控词表，题库质量是天花板 |
| 成长时间线 | ★★★☆☆ | 消费侧（展示/筛选/跳转）完成，生产侧（事件写入）有 9 条规则无写入点 |

## 1. 现状盘点

### 1.1 数据模型：一张表、两个维度

`portal_interview_question` 采用双维度正交设计：

- **question_type（内容分类）**：bagwen / algorithm / system_design / project / hr —— 这道题考什么
- **practice_mode（练习模式）**：reading / choice / coding —— 用户怎么练这道题

这个设计本身是对的。参考业内：力扣用"标签+题型"描述内容、题型隐含作答方式；牛客把"八股选择题库"和"编程题库"作为两个子频道共享一套底层。**"内容分类"和"作答方式"确实是两个维度**——一道系统设计题既可以纯阅读（面经式），也可以做成选择题。

**但落地现状把正交用塌了：**

| 证据 | 说明 |
|------|------|
| DML 种子数据只有 8 题 | 5 道 `bagwen+choice`（带完整 options/correct_answer/analysis）+ 3 道 `algorithm+coding`（带 solution/解析），**0 道 reading 模式** |
| 前端实际用 questionType 路由 | `PracticeChoiceListPage` 用 `questionType: 'bagwen'` 筛选、`PracticeCodingListPage` 用 `questionType: 'algorithm'` 筛选（v10.16 修复空列表 Bug 时改的，当时判断种子数据没有 practice_mode——实为 DB 与 DML 漂移） |
| 结果 | 前端语义变成"bagwen=选择题、algorithm=编程题"，**双维度塌缩成一对一映射**。一旦运营按设计文档录入 reading 模式的 bagwen 题，选择题列表就会出现点进去是纯阅读的"假选择题" |

> 注：2026-08-30 会话中已把题目详情页改为纯阅读模式、选择题列表跳详情页，这些是**症状级修复**——它们让页面可用，但加深了"bagwen=阅读"的语义绑定。本方案第 4 节会用系统性设计取代它们。

### 1.2 前台页面：两个入口、三套实现

**页面清单：**

| 入口 | 页面 | 路由 | 现状 |
|------|------|------|------|
| 面试专区 | 题库列表 | `/interview/questions` | 筛选维度最全（分类/难度/题型/关键词/推荐） |
| 面试专区 | 题目详情 | `/interview/question/:id` | 2026-08-30 改为纯阅读（移除答题/判题/提交历史） |
| 学习中心 | 刷题中心 | `/learn/practice` | 两个卡片入口（选择题/编程题） |
| 学习中心 | 选择题列表 | `/learn/practice/choice` | **代码与编程题列表 90% 重复**，questionType=bagwen |
| 学习中心 | 选择题做题 | `/learn/practice/choice/:id` | 有路由有页面，但列表不跳它（跳详情页），**空挂路由** |
| 学习中心 | 编程题列表 | `/learn/practice/coding` | questionType=algorithm，跳做题页 |
| 学习中心 | 编程题做题 | `/learn/practice/coding/:id` | Monaco 编辑器 + 样例用例 + OJ 判题 |
| 我的 | 成长时间线 | `/growth/timeline` | 展示/筛选/滚动加载/跳转 targetUrl，消费侧完整 |

**三个断链/混乱点：**

1. **跳转规则三处三个样**：选择题列表 → 详情页（阅读）；编程题列表 → 做题页；题库列表 → 详情页。同一道题从不同入口进入，交互模式完全不同，用户无法建立稳定预期。
2. **`/learn/practice/choice/:id` 空挂**：路由、组件、判分 API 都在，但没有任何页面链接到它。
3. **列表页 90% 重复**：`PracticeChoiceListPage` 与 `PracticeCodingListPage` 除 `questionType` 取值和跳转目标外几乎相同；它们与 `QuestionListPage` 又重复一遍查询/分页/筛选骨架。题型/难度徽章映射在 `QuestionListPage` 与 `QuestionDetailPage` 各写一份。

### 1.3 后端链路：两套提交、互不知晓

这是**本次评审发现的最严重问题**：

```
链路A：POST /portal/interview/question/{id}/submit  (submitAnswer)
  ├─ choice 模式：服务端比对 correct_answer 判分 ✓ 判分真实
  ├─ reading 模式：提交即完成 ✓
  ├─ coding 模式：仅检查 code 非空 → 标记 isSuccess=true ✗【不判题，形同虚设】
  ├─ 写 portal_interview_submission ✓
  └─ recordEvent("interview","solve_question") ✓【成长事件只在这里发】

链路B：POST /portal/judge/submit  (submitJudge)
  ├─ 拉取测试用例 → Process/Docker 沙箱真实判题 ✓
  ├─ 写 portal_interview_submission（PENDING→终态）✓
  └─ recordEvent ✗【判题通过不发成长事件】
```

**后果**：前端编程题做题页走链路B，所以**用户做对编程题，成长时间线上什么都没有**；若走链路A 的 coding 分支，则记录"通过"但实际没判题——**两条路都是错的**。v10.16 的 devlog 记录"四大断链全部修复"，实际是前端接上了链路B，但链路A 的 coding 分支和成长事件缺口留了下来。

**其它后端问题：**

| 问题 | 证据 |
|------|------|
| submission.status 枚举与 JudgeStatus 枚举命名不一致（time_limit vs TIME_LIMIT_EXCEEDED） | 表注释 vs JudgeStatus 枚举 |
| options 在 DDL 是 JSON 类型、Java 实体是 String，靠前端 JSON.parse 兜底 | PortalInterviewQuestion.java |
| 少数 receive_* 类成长规则（9 条）配置了但代码里无 recordEvent 写入点 | portal_growth_rule vs grep recordEvent |
| daily_login 规则存在但无触发代码 | 同上 |

### 1.4 成长事件：消费完整、生产缺半

成长规则表共 30 条规则、5 个模块。与题库相关的关键事件现状：

| 行为 | 规则配置 | 实际写入 | 时间线可见 |
|------|---------|---------|-----------|
| 选择题做对 | interview/solve_question +10/日限20 | ✓（submitAnswer） | ✓ |
| 编程题 AC | interview/solve_question | **✗（judge 链路不发）** | ✗ |
| 阅读模式看题 | 无规则 | **✗ 无任何记录** | ✗ |
| 读文章/读书 | article/reading 模块齐全 | ✓ | ✓（时间线 module 筛选只有 article/reading/interview） |
| 每日登录 | all/daily_login +1 | ✗ 未接线 | ✗ |

对照项目介绍文档的定位——"把学习、刷题、面试、阅读、写作整合为一条成长时间线"——**刷题（编程题）和看题（阅读）恰好是缺的**。而读书模块已经有 `finish_book`、章节进度上报（`portal_reading_progress`）的成熟先例，题库完全可以照抄这套模式。

## 3. 5W2H 框架分析

### What —— 做什么？目标是什么？

**目标一句话：把题库做成"一套数据、三种模式、按模式分发、全程留痕"的学习平台核心资产。**

具体交付四件事：

1. **链路收口**：三种练习模式各有一条端到端完整闭环（列表→进入→作答→判分→解析→成长事件→时间线）
2. **共用/独立归位**：公共能力组件化/服务化，模式差异各自封装
3. **阅读行为记录**：看题也是学习行为，进时间线、进统计
4. **AI 数据底座准备**：题库结构化字段可作为 AI 面试出题与画像回流的受控数据源

**明确不做的（防蔓延）**：
- 不做多题库/多表拆分（统一一张表的设计保留）
- 不在本期做题目众包/UGC 出题
- 不在本期做面试题库与刷题入口合并成单一页面（两个入口的场景定位不同，保留，见 How）
- 不做实时判题流式输出、竞赛排名等 OJ 高级特性

### Why —— 为什么做？

1. **平台定位要求**：项目介绍文档明确差异化=AI 语音面试官 + OJ 判题 + 成长时间线。题库是前两者的数据源、后者的行为源——三差其二（编程题事件断链、阅读无记录），等于差异化承诺没兑现
2. **内容复利要求**：题库后期要作为知识库给 AI 面试用（文档已规划出题四路：简历深挖/薄弱点/随机兜底/行业RAG）。数据不结构化、标签不受控，AI 消费价值就低
3. **留存要求**：成长时间线是"让用户知道自己有没有进步"的情感锚点。做题是最高频的学习行为，不进时间线等于核心行为无反馈
4. **工程成本**：三处复制的列表页 + 双轨提交链路，每加一个需求都在放大维护成本；现在收口的成本远低于功能继续膨胀后

### Who —— 谁来做？相关人是谁？

| 角色 | 职责 |
|------|------|
| 你（平台开发/架构） | 后端链路收口、事件补全、前端组件归一 |
| 运营（内容录入方） | 按 practice_mode 正确录题、补 reading 题量、维护 knowledge_tags 受控词表 |
| AI 模块（数据消费方） | 语音面试出题、画像弱项回流——对题库字段提出消费契约 |
| 用户（求职者） | 最终受益人：练有反馈、看有记录、时间线有内容 |
| 管理后台（维护方） | 录题表单已支持三模式，需增加数据校验（choice 必须有 options、coding 必须有用例） |

### When —— 什么时候做？

**三期推进，P0 立即开始：**

| 阶段 | 时间盒 | 内容 | 验收标准 |
|------|--------|------|---------|
| P0 链路收口 | 3~5 天 | 编程题成长事件补全、列表筛选语义改回 practice_mode、数据回填 | 三种模式各做一题，时间线都有记录 |
| P1 体验归位 | 1~2 周 | 列表组件归一、详情↔做题互跳、阅读事件、时间线学习筛选 | 三个列表页一份实现；看题 1 分钟后时间线可见 |
| P2 数据底座 | 视运营节奏 | knowledge_tags 受控词表、题库→AI 检索适配、画像回流 | AI 面试能按弱项标签出题 |

### Where —— 从哪里入手？

**从后端 `submitAnswer` 与判题服务的收口入手，而不是从页面改起。**

理由：页面混乱（跳转不一致、空挂路由、复制粘贴）都是**链路断裂和数据漂移的症状**。先修页面会继续在错误语义上叠代码（本次会话的"选择题列表跳详情"就是例子——它让页面能用，但把 bagwen=阅读绑得更死）。根因在后端提交网关和数据，先定契约，前端按契约重排。

### How —— 怎么做？用什么方法？

（详细方案见第 4 节，此处为方法框架：六步法）

1. **定语义**：明确 question_type=内容、practice_mode=作答方式，前端一切筛选/路由/渲染以 practice_mode 为准
2. **收链路**：submitAnswer 成为唯一做题提交入口，coding 分支内部调用判题服务；判题终态统一回调成长事件
3. **补数据**：DB 回填 practice_mode；管理端录题校验模式配套字段
4. **归组件**：列表页抽成 QuestionListPage 组件（props: mode/filters）；题型/难度映射抽 composable
5. **接事件**：read_question 事件 + 前端阅读时长上报；时间线加"学习"筛选
6. **备底座**：knowledge_tags 受控词表（字典表），题库检索适配器供 AI 出题用

### How much —— 需要多少成本？做到什么程度？

**开发成本估算：**

| 工作项 | 量级 | 说明 |
|--------|------|------|
| 后端链路收口 | 约 3~4 个文件改动 | submitAnswer coding 分支、judge 回调、事件补发 |
| 数据回填 | 1 条 SQL + 脚本 | 存量题按规则回填 practice_mode |
| 前端列表归一 | 新建 1 组件 + 删 2 页面 | PracticeChoiceList/PracticeCodingList 合并为一个组件 |
| 详情/做题互跳 | 2 个文件 | 加"去练习/看解析"入口按钮 |
| 阅读事件 | 后端 1 接口 + 前端 1 埋点 | 仿照读书进度上报 |
| 时间线学习筛选 | 后端 1 枚举 + 前端 1 tab | module 增加 learn |

**做到什么程度（分档）：**

- **及格线（P0）**：三种模式做题/看题，行为都进时间线——平台差异化承诺兑现
- **良好线（P1）**：代码归一，改一处生效三处；动线完整（看→练→解析→记录）
- **优秀线（P2）**：题库成为 AI 出题的受控数据源，弱项标签回流出题，形成"练习→暴露弱项→AI 针对性面试→再练习"的增长飞轮

**不做/后置的成本**（避免过度设计）：
- 多语言判题沙箱扩展（Java/Go 等）——用例够用前不扩
- 题目版本管理、贡献者体系——运营单人录入阶段无必要
- 阅读时长精确统计（防作弊级）——日上限 + 简单阈值即可

## 4. 目标架构设计

### 4.1 共用与独立的划分矩阵（核心原则：该共用的公用，该独立的独立）

| 能力 | 三模式共用 | choice 独有 | coding 独有 | reading 独有 |
|------|-----------|------------|------------|--------------|
| 题目表/实体/管理端录题 | ● | | | |
| 列表查询（分页/筛选/搜索） | ● | | | |
| 列表页 UI 组件 | ●（props 区分） | | | |
| 题目头部卡（题型/难度/标签/公司/点赞/收藏） | ● | | | |
| 详情页骨架 + 解析区（大纲/参考答案/评分标准） | ● | | | |
| 提交记录表 portal_interview_submission | ● | | | |
| 成长事件 solve_question | ● | | | |
| 提交网关 submitAnswer | ●（模式分支） | | | |
| 选项渲染 + 单选/多选 + 服务端判分 | | ● | | |
| Monaco 编辑器 + 语言选择 | | | ● | |
| 测试用例 + OJ 沙箱判题 + 运行时/内存 | | | ● | |
| 阅读时长上报 + 阅读事件 | | | | ● |
| 阅读进度/已读标记 | | | | ● |

### 4.2 数据模型：保留双维度，加"派生规则"

不改表结构，只明确规则：

1. **practice_mode 是前端路由/渲染的唯一依据**；question_type 仅用于内容筛选与展示徽章
2. **模式配套字段强校验**（后端录题与导入时）：
   - `choice` → options 必填（≥2 项且恰有 1 个或明确的多个 is_correct）+ correct_answer 必填 + analysis 必填
   - `coding` → 至少 1 条测试用例（is_sample≥1）；solution 建议填
   - `reading` → reference_answer 或 analysis 至少一项
3. **存量数据回填**（一次性 SQL）：无 options 的 bagwen → reading；有用例的 algorithm → coding；其余保持默认
4. options 建议后端 VO 直接返回结构化数组（服务端 parse，前端不再 JSON.parse 兜底）

### 4.3 前端：一组件三路由 + 模式分发跳转

```
列表层（归一）：
  /interview/questions        → QuestionBankPage(mode=all)      题库总入口（三模式混合 + 模式筛选器）
  /learn/practice/choice      → QuestionBankPage(mode=choice)   三个路由共用一个组件
  /learn/practice/coding      → QuestionBankPage(mode=coding)   差异只有 props + SEO 文案

跳转规则（列表点击，按 practice_mode 分发）：
  reading → /interview/question/:id   （纯阅读详情）
  choice  → /learn/practice/choice/:id（做题页）
  coding  → /learn/practice/coding/:id（做题页）
  列表卡片上同时提供副入口"查看详情"（小图标），保证任何时候可进入阅读

详情 ↔ 做题互跳：
  做题页（choice/coding）头部提供「查看完整解析」→ 详情页
  详情页对 choice/coding 题提供「去练习」主按钮 → 对应做题页
  阅读题（reading）详情页不显示练习按钮
```

**组件归一清单：**

| 抽取物 | 形式 | 替代 |
|--------|------|------|
| `QuestionBankListPage.vue` | 组件 + props(mode) | PracticeChoiceListPage / PracticeCodingListPage 两份代码 |
| `useQuestionMeta()` | composable | 两个页面里的题型/难度映射字典 |
| `QuestionHeaderCard.vue` | 组件 | 详情页/做题页重复的头部卡 |
| `AnswerAnalysisSection.vue` | 组件 | 详情页解析区（大纲/参考答案/评分标准），做题页答后复用 |

### 4.4 后端：统一提交网关（收口双轨）

**方案：submitAnswer 作为唯一做题入口，判题成为它的内部能力。**

```
POST /portal/interview/question/{id}/submit
  ├─ reading  → 记录已读（可带笔记）→ recordEvent(solve_question/read_question)
  ├─ choice   → 服务端判分 → 落 submission → recordEvent(solve_question)
  └─ coding   → 内部调用 JudgeService：
        同步模式：判题 → 落 submission(终态) → recordEvent(solve_question)
        异步模式：落 submission(PENDING) 返回 submissionId
                  → 前端轮询 /portal/judge/result/{id}
                  → 判题终态回调处 recordEvent(solve_question)【补当前缺口】

/portal/judge/submit 保留为纯 OJ 能力（沙箱调试用），前端做题页不再直连
```

同时修正：submission.status 与 JudgeStatus 枚举统一命名（后端内部映射层转换）。

### 4.6 题库作为 AI 面试数据底座（系统设计视角）

题库对 AI 面试的价值分三层，按依赖顺序：

**第一层：出题源（已有设计，直接复用）**
- 语音面试四路出题中的"随机兜底题"直接查题库；"薄弱点出题"按 knowledge_tags 匹配

**第二层：结构化知识（本期要打的地基）**
- `examine_points / answer_outline / reference_answer / analysis / knowledge_tags` 五个字段是题库区别于普通题面的增值数据
- 关键动作：**knowledge_tags 升级为受控词表**（字典表 + 管理端选择而非自由填写），否则标签发散后 AI 按标签出题/画像回流全部失效
- 题库内容可选同步入 `ai_knowledge_library` 触发向量化，支撑"行业 RAG 出题"第 4 路（当前规划中但无数据）

**第三层：画像回流（闭环飞轮）**
```
做题对错 → submission 聚合出 knowledge_tags 掌握度 → 弱项标签
→ 刷新用户画像（复用语音面试的 refreshWeakTags 机制）
→ AI 面试针对弱项加权出题 → 错题进错题本（WrongQuestionService 已有）
→ 再练习 → 掌握度回升
```
这是"练习暴露弱项 → AI 针对性考 → 再练习"的增长飞轮，**前提是第一、二层的数据契约先立住**。

## 6. 风险与权衡

| 风险 | 应对 |
|------|------|
| 改列表筛选语义后，若运营已录入一批"bagwen 但无 options"的题，选择题列表会空 | 先跑回填脚本（P0-3），再上线前端改动；顺序不可颠倒 |
| 阅读时长上报可刷分 | 低分值（+2）+ 日上限 + 同题同日幂等，够用不过度 |
| 异步判题回调发事件的事务边界（判题成功但事件失败） | 事件发送 try-catch 不回滚判题结果（与现有文章模块模式一致），补对账即可 |
| 题库存量质量参差，AI 出题效果差 | P2 前先做内容抽检，宁少勿滥（AI 出题质量=题库质量天花板） |
| 三模式平衡可能演变为"三套功能都要全" | 以共用矩阵（4.1）为护栏：新增能力先问"这是模式差异还是公共能力" |

## 7. 结论

**应不应该做？——应该，而且优先级高于新功能。** 题库是平台三大差异化（AI 面试、OJ 判题、成长时间线）的交汇点：它是 AI 面试的题源、OJ 的内容载体、成长时间线最高频的行为来源。当前"三种模式只有一种完整闭环"的状态，等于三个差异化承诺都打了折扣。

**怎么做？——先收口，再归一，后底座。** P0 修链路（判题事件断链、数据回填、筛选语义），P1 归组件（删复制、通动线、补阅读记录），P2 备底座（受控标签、AI 检索适配、画像回流）。顺序不可颠倒：数据与链路的根因不修，页面层怎么调都是在错误的语义上叠功能。

**怎么衡量做成了？** 一个新用户从 `/learn` 进入：选择题做对 → 时间线 +10；编程题 AC → 时间线 +10、提交记录可见；reading 题停留一分钟后 → 时间线 +2；学习中心仪表盘正确率/连续天数随之变化；AI 语音面试能按他的弱项标签出题。**四条全通，这个模块才算"有用可行的平台"。**
