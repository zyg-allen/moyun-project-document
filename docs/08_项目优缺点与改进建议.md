# 项目优缺点与改进建议

> 版本：v5.2 | 更新日期：2026-07-19 | 用途：后期开发指导

本文档基于 v5.2 全面评审，系统梳理项目优缺点，为后期开发提供指导。

---

## 一、优点（值得保持）

### 1.1 架构层面

| 优点 | 说明 | 应保持的做法 |
|---|---|---|
| **技术栈现代统一** | Spring Boot 3.3 + Java 21 + Vue 3 + Vite 5，无历史包袱 | 新模块继续用最新稳定版 |
| **后端分层清晰** | portal/ext.cms/ext.generator/ext.job/system 各包内 controller/service/mapper/domain 四层齐备 | 新模块遵循四层结构 |
| **domain 分 DDD 风格** | entity（持久化）/query（查询入参）/vo（视图出参）分离 | 新实体继续三分法 |
| **双 SecurityFilterChain** | 门户与后台独立认证，互不干扰 | 新增认证域时新建 FilterChain |
| **多类型存储** | MySQL + MongoDB + Redis + MinIO 各司其职 | 按数据特性选存储 |

### 1.2 业务层面

| 优点 | 说明 | 应保持的做法 |
|---|---|---|
| **业务规模可观** | 9 大领域 169 张表 113 Controller，是真正的产品 | 继续按业务域扩展 |
| **成长体系闭环** | recordEventWithTarget 统一埋点，规则未配置安全返回 0 | 新业务行为接入成长体系 |
| **积分打赏 MVP** | 用积分替代真实资金，绕开支付资质 | 先验证产品逻辑，后接真实支付 |
| **双用户体系** | portal/sys 独立认证，私信支持跨用户体系 | 新增用户类型时扩展 user_type |
| **AI 能力集成** | LangChain4j + 通义大模型，AI 模拟面试 + 创作者辅助 | 新 AI 场景继续用 LangChain4j |

### 1.3 工程层面

| 优点 | 说明 | 应保持的做法 |
|---|---|---|
| **SQL 整理完成** | 90 脚本 → 12 文件，169 表合并 ALTER 到最终 CREATE | 新表直接加到 sql-organized |
| **幂等设计成熟** | CREATE IF NOT EXISTS + INSERT IGNORE + information_schema 检查 | 新脚本必须幂等 |
| **死接口清理运动** | 所有 portal controller 顶部都有清理说明 | 新 controller 注明在用接口 |
| **版本日志** | devlog.md 详细式日志覆盖全部版本变更 | 每版本更新 devlog |
| **文档体系化** | docs/ 下 10 篇编号文档覆盖概述/架构/开发/部署/测试/修复/日志 | 新模块补设计文档 |

### 1.4 代码质量亮点

| 优点 | 位置 | 应保持的做法 |
|---|---|---|
| **原子计数器** | 文章模块 `incrementLikes/Comments/Views` 用 `count = count + delta` + `GREATEST` 防负数 | 所有计数器统一此模式 |
| **ChapterReaderPage 竞态守卫** | `const seq = ++loadSeq` + 多处 `if (seq !== loadSeq) return` | 异步页面参照此模式 |
| **ResumeEditPage 表单状态机** | saveStatus(idle/saved/saving) + onBeforeRouteLeave 未保存提示 | 表单页参照此模式 |
| **useMessageStore 跨组件同步** | Pinia 单例同步 Navbar 铃铛与 MessagesPage 未读数 | 跨组件状态用 store |
| **SEO 元信息完整** | 每页 useHead(generateSeo) + 404 路由 + scrollBehavior | 新页面必须 SEO |
| **安全配置规范** | JWT 密钥环境变量、敏感配置 gitignore、双 SecurityFilterChain | 新配置走环境变量 |

## 二、缺点（需正视）

### 2.1 安全层面（v5.2 已修复主要问题，但仍有遗留）

| 缺点 | 严重度 | 现状 | 后期建议 |
|---|---|---|---|
| **代码执行无沙箱** | 致命 | 临时下线 | 迁移到 Docker/gVisor，限制网络/文件/seccomp |
| **存量明文密码** | 高 | 新用户已加密，存量未迁移 | 强制改密或批量加密迁移 |
| **无限流覆盖不足** | 中 | 仅 login/register/comment 3 处 | 关键接口全量加 @RateLimiter |
| **XSS 过滤器未覆盖 portal/cms** | 中 | `xss.urlPatterns` 仅 `/system/*,/monitor/*,/tool/*` | 扩展到 portal/cms |
| **验证码极弱** | 中 | math 类型 + length=2 | 改 char 类型 + length=4 + 干扰线 |
| **密码无复杂度** | 中 | 仅长度 5-20 | 加大小写+数字+特殊字符要求 |
| **无敏感词过滤** | 中 | 所有 UGC 无审核 | 接入阿里云内容安全/腾讯天御 |
| **无隐私政策** | 中 | 无用户协议/隐私政策 | 撰写 + 提供账号注销接口 |

### 2.2 数据层面

| 缺点 | 影响 | 后期建议 |
|---|---|---|
| **status 字段类型 4 种混用** | char(1)/varchar(1)/varchar(16)/varchar(20) + 3 种取值体系 | 规范：状态机 varchar(20)+字符串值；开关 char(1)+0/1 |
| **仅 portal_user 有 del_flag** | 逻辑删除策略不一致 | UGC 表统一加 del_flag |
| **7 张表缺审计字段** | portal_message/portal_tip_order 等 | 补齐 create_by/create_time/update_by/update_time/remark |
| **portal_message 缺 sender_id 索引** | "我发送的消息"全表扫描 | 加 idx_sender_id |
| **portal_user.birthday 用 VARCHAR(20)** | 类型不规范 | 改 DATE |
| **无 Flyway** | 89 脚本靠手工执行 | 引入 Flyway 自动化版本管理 |

### 2.3 后端代码层面

| 缺点 | 影响 | 后期建议 |
|---|---|---|
| **55+ 死 Service 方法** | 代码膨胀 | 全量核对调用方，删除死代码 |
| **N+1 查询** | 性能 | 改批量查询或 JOIN |
| **API 路径混乱** | 单复数混用、驼峰连字符混用 | 制定 API 命名规范并重构 |
| **两个 Controller 共享 @RequestMapping** | PortalArticleController 与 VersionController 都用 `/portal/article` | VersionController 改 `/portal/article/version` |
| **分页 pageSize 未限制上限** | 14 处直接 `new Page<>(pageNum, pageSize)` | 统一走 PageUtils.safePageSize |
| **8 个 Cms*Controller 误放 portal/controller 包** | 模块边界破坏 | 迁移到 ext/cms/controller |
| **事务 rollbackFor 不统一** | 部分未指定 | 统一 `@Transactional(rollbackFor = Exception.class)` |

### 2.4 前端 portal 层面

| 缺点 | 影响 | 后期建议 |
|---|---|---|
| **18 处重复 toast** | 代码冗余 | 统一用 useToast |
| **10 处内联 Avatar** | 不一致 | 统一用 Avatar 组件 |
| **15 处内联 Empty** | 不一致 | 统一用 Empty 组件 |
| **60+ 处 as any** | 类型安全形同虚设 | 补全类型定义 |
| **token 明文存 localStorage** | XSS 可窃取 | 改 HttpOnly Cookie |
| **18 处 window.confirm** | 体验差 | 替换为 useConfirmModal |
| **CodeRunnerPage z-40 冲突** | 抽屉遮罩与 TabBar 同级 | 调整 z-index 层级 |

### 2.5 前端 admin 层面

| 缺点 | 影响 | 后期建议 |
|---|---|---|
| **9 个页面零权限校验** | article(3页)+interview(6页) v-hasPermi 命中 0 | 补 v-hasPermi |
| **4 个 cms 页面权限命名空间错位** | portal:ad:* 对应 /cms/ad/* 路径 | 统一命名空间 |
| **cms 完全未用 useDict** | 状态枚举硬编码 | 改用字典 |
| **MessageBell 跨工程重复** | 与 portal NotificationBell 重复 | 抽公共组件 |

### 2.6 部署与运维

| 缺点 | 影响 | 后期建议 |
|---|---|---|
| **无 Dockerfile** | 部署依赖手工 | 提供 Dockerfile + docker-compose |
| **无 CI/CD** | 无自动化 | GitHub Actions：lint → test → build → docker push |
| **无 nginx 配置** | 无生产模板 | 提供 nginx.conf 模板（gzip/缓存/HTTPS）|
| **无生产配置模板** | 部署易出错 | application-prod.yaml.example（已创建）|
| **无监控告警** | 故障不可见 | Prometheus + Grafana + 告警 |

### 2.7 合规层面

| 缺点 | 风险 | 后期建议 |
|---|---|---|
| **无敏感词过滤** | 违规内容风险 | 接入内容安全 API |
| **无实名核验** | 创作者认证不严谨 | 接入公安二要素/三要素 |
| **无隐私政策** | 合规处罚 | 撰写用户协议 + 隐私政策 |
| **读书模块版权** | 侵权风险 | 上传书籍需 ISBN 校验 + DMCA 流程 |
| **无被遗忘权接口** | GDPR/个保法 | 提供账号注销 + 数据导出 |

## 三、改进建议（按优先级）

### 3.1 P0 立即处理（本周-本月）

1. **代码执行沙箱化**
   - 当前：临时下线返回 503
   - 目标：Docker 容器隔离，限制网络出口、只读根文件系统、seccomp 限制系统调用
   - 工作量：1-2 周

2. **存量明文密码迁移**
   - 当前：新用户已 BCrypt，存量用户仍是明文
   - 目标：强制改密 或 批量 BCrypt 加密（需临时登录态迁移）
   - 工作量：3-5 天

3. **真实支付通道接入**
   - 当前：积分打赏绕过支付，付费阅读购买被拦截
   - 目标：接入微信/支付宝，积分打赏逻辑保留为"免费模式"
   - 工作量：2-4 周（含资质申请）

### 3.2 P1 本月内（2-4 周）

4. **死接口全量清理**
   - 核对 55+ 个 Service 方法的调用方

6. **Docker 化部署**
   - Dockerfile + docker-compose.yml（含 MySQL/Redis/MinIO 一键起）

7. **Flyway 引入**

8. **admin 9 个无权限页面补 v-hasPermi**

## 五、后期开发指导原则

### 5.1 安全第一
- 所有新功能先做安全评审（越权/注入/XSS/SSRF）
- 密码/JWT/凭据必须环境变量化
- UGC 内容必须过滤
- 文件上传必须白名单

### 5.2 幂等优先
- SQL 必须 CREATE IF NOT EXISTS + INSERT IGNORE
- 计数器必须原子 SQL
- 删除必须级联清理
- 越权必须归属校验

### 5.3 先验证后投入
- 新功能先 MVP（如积分打赏绕过支付）
- 验证产品逻辑后再投入完整实现
- 避免过度设计

### 5.4 文档同步
- 每版本更新 devlog.md
- 新模块补设计文档
- 设计文档状态字段及时更新（"待评审"→"已实施"）

### 5.5 测试保障
- 新功能必须有测试用例（05_测试清单）
- 关键链路纳入 10_功能排查清单
- 上线前跑一遍测试清单

### 5.6 技术选型保守
- 不盲目追新，用稳定版
- 新引入依赖需评审（安全/性能/维护性）
- 优先复用已有组件

## 六、总体评估

### 6.1 当前状态（v5.2）

| 维度 | 评分 | 说明 |
|---|---|---|
| 架构设计 | 7/10 | 技术栈现代，分层清晰，但模块边界有破坏 |
| 后端代码 | 6/10 | 业务完整，但死代码多、计数器非原子（已修复）|
| 前端 portal | 6/10 | 页面丰富，但重复代码多、类型安全弱 |
| 前端 admin | 6/10 | 功能完整，但权限覆盖不全 |
| 数据库 | 6/10 | 表设计合理，但类型混用、无 Flyway |
| 安全 | 5/10 | v5.2 修复后大幅提升，但仍有遗留 |
| 部署运维 | 3/10 | 无 Docker/CI/CD/监控 |
| 文档 | 7/10 | 体系完整，但部分滞后 |
| **综合** | **6/10** | **业务广度可观，工程化待提升** |

### 6.2 后期发展建议

**短期（1-2 个月）**：聚焦安全加固 + 工程化（Docker/Flyway/死代码清理），不增加新业务功能

**中期（3-6 个月）**：接入真实支付通道，激活商业化（付费阅读/创作者分成/VIP），前端组件统一

**长期（6+ 个月）**：AI 能力深化，移动端优化，国际化，性能优化

### 6.3 核心建议

> **先做减法，再做加法**

1. **减法**：清理死代码、统一规范、补全测试、Docker 化
2. **加法**：新业务功能、AI 能力、移动端

> **先活下去，再活得好**

1. **活下去**：安全合规、稳定部署、核心闭环
2. **活得好**：商业化、用户体验、性能优化
