> 日期：2026-10-22
> 环境：本机 `127.0.0.1:8080`（开发实例，dev 配置），MySQL/Redis 同机
> 工具：零依赖 Node 脚本（`perf-scripts/loadtest.js`、`webcheck.js`）
> 数据：`ledger_transaction` 仅 5 行 —— 本报告测的是**代码路径与资源上限**，不是数据量压力

## 1. 方法

- 混合负载：`dashboard` / `transactions 分页` / `reports 年度` / 字典（匿名）四接口轮询；
- 并发梯度：1（基线）、10、20、40，各 20 秒；
- 单接口隔离：40 并发、15 秒，分别打 `txn-page` / `dashboard` / `report`；
- 指标：RPS、p50/p95/p99、失败数、平均响应体大小；
- 无 think time（比真实用户更激进，结果偏保守）。

## 3. 根因分析

`txn-page` 是唯一明显劣化的接口，且与数据量无关（表里只有 5 行）。代码路径：

`LedgerTransactionServiceImpl.pageTransactions()` 每次请求执行 **5 次 SQL**：

1. `COUNT(*)`（分页总数）；
2. 分页查询（`ORDER BY transaction_date DESC, id DESC`）；
3. `fillDisplayNames()` 内 3 次 `selectBatchIds`（资产账户、负债、分类）。

叠加 **HikariCP 未显式配置 → 默认最大连接数 10**：

```
容量 ≈ 连接数 / 单请求占用时长 ≈ 10 / (5 × 20ms) ≈ 100 RPS
```

实测 97 RPS，与推算一致。并发升高时请求在连接池排队，p50 从 20ms 涨到 512ms。

## 4. 优化建议（按性价比）

| 优先级 | 措施 | 预期 |
|---|---|---|
| **P0** | 显式配置 `spring.datasource.hikari.maximum-pool-size: 20~30`（配合 DB `max_connections`） | txn-page 容量约提升 2~3 倍 |
| **P0** | `fillDisplayNames` 改为**单条 JOIN 查询**（或一次性 `IN` 查三表合并），把 5 次 SQL 降到 2 次 | 单请求耗时降 ~60% |
| P1 | 名称映射加 Redis 缓存（分类/账户名变化少，TTL 5~10 分钟） | 再次降到 2 次 → 查询为主 |
| P1 | 生产库补复合索引 `(user_id, status, transaction_date, id)` | 大数据量下的排序/分页 |
| P2 | 列表页可不返回精确 `total`（"是否还有下一页"用 `pageSize+1` 探测），去掉 COUNT | 大表下明显 |
| P2 | 压测脚本升级为 k6/locust，纳入 CI（可选） | 可持续回归 |

## 5. Web 体检

### 5.1 响应头

| 目标 | 状态 | 压缩 | 安全头 |
|---|---|---|---|
| 后端 API | 200 | ❌ 无 gzip（106B，可忽略） | `X-Frame-Options: SAMEORIGIN`、`X-Content-Type-Options: nosniff`；缺 CSP / HSTS / Referrer-Policy / Permissions-Policy |
| H5 开发服务器 | 200 | ❌ 无 gzip、`cache-control: no-cache` | 无（Vite dev，预期） |
| 管理后台（Vite dev） | 200 | ❌ 无 gzip、cache-control: no-cache | 无（dev 预期）；127.0.0.1:80 被 Steam++ 占用，需用 localhost 访问 |

### 5.2 产物体积（后台优化后）

| 产物 | 优化前 | 优化后 |
|---|---|---|
| 后台首屏 | 2 请求 / **940.8 KB gzip** | 2 请求 / **556.5 KB gzip（-41%）** |
| 后台总体积 | 12.4 MB（gzip 3.7 MB） | 9.9 MB（gzip 3.1 MB） |

优化项：移除未使用的 VForm3（全量注册但无页面使用）、ECharts 改按需引入（line/bar/pie/scatter/gauge + grid/tooltip/legend/title/dataset/dataZoom/canvas）、保留 Vite 默认分包。
（尝试过 manualChunks 强制拆包，反而把共享 chunk 提前拉进首屏，已回退。）

### 5.2.1 产物体积（优化前基线）

| 产物 | 原始 | gzip | 最大单文件 |
|---|---|---|---|
| H5（`dist/build/h5`） | 868 KB | **267 KB** | `index.js` 278 KB → 96.5 KB |
| 管理后台（`dist`） | **12.4 MB** | **3.7 MB** | `index-C20dpGFt.js` 3.28 MB → 874 KB；另有 2.4 MB / 1.6 MB / 1.0 MB 多个大 chunk |

**结论**：

- H5 体积健康（首屏主包 gzip 约 97 KB），在 5Mbps 带宽下首屏可接受；
- **管理后台过重**：首屏 JS 单文件 gzip 873.7 KB（+ CSS 67.1 KB），5Mbps 下仅主包就约 1.5 秒，弱网体验差；
- 建议后台做 **vendor 拆分 + 路由懒加载 + 图表/编辑器按需引入**，目标主包 gzip < 300 KB。

### 5.3 生产部署要求（当前仓库未配置）

- Nginx 开启 `gzip`（或 brotli）；
- 带 hash 的静态资源：`Cache-Control: public, max-age=31536000, immutable`；
- `index.html`：`no-cache`；
- 补安全头：`Content-Security-Policy`、`Referrer-Policy`、`Permissions-Policy`、HTTPS 下 `Strict-Transport-Security`。

## 6. 限制与说明

1. 压测对象是本机**开发实例**，非生产；无网络延迟、无反向代理、无 TLS；
2. 数据量极小，未覆盖大数据量下的索引/排序问题；
3. 127.0.0.1:80 被 Steam++ 占用，后台需用 http://localhost/ 访问（已按此重测）；\r\n4. 压测期间曾**临时关闭图形验证码**以获取测试 token，结束后已恢复（`sys.account.captchaEnabled=true`），并删除了临时账号 `perf_probe`；
5. 建议生产前用 k6 在预发环境复测，并加入慢 SQL 监控（`log_min_duration_statement` / Druid 慢 SQL）。
