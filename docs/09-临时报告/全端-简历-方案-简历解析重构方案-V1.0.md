# 全端-简历-方案-简历解析重构方案-V1.0

> **版本**：V1.0　**日期**：2026-09-29　**状态**：方案评审（待裁决）
> **范围**：`moyun-server` 简历解析链路（`ResumeParseService` / `AiTaskHandler` 体系 / `PortalUserResumeController`）+ `moyun-portal` 简历编辑与面试准备页
> **关联**：本文是**评估与设计依据**，落地前需先裁决 §9 的开放问题

---

## 1. 背景：本文档要解决的问题

简历解析（Resume Parsing）是平台的**上游数据入口**，它的质量会向下游**双重传导**：

| 下游 | 受影响方式 |
|---|---|
| **在线简历编辑表单** | 用户上传后需把内容**反显**到统一格式的表单（`UserResumeVO`）；抽错了用户就得手改，直接决定体验 |
| **AI 面试 / 岗位匹配** | 简历内容是**面试提问与评估的核心上下文**；抽漏了 → 面试问不到点上、评估失真 |

**现状问题**（实测，非推测）：
1. **本地环境 100% 解析失败**（MinIO 误判 + 磁盘路径拒绝），且失败后**不回滚** → 每次失败留一条空简历（脏数据）
2. **AI 关闭时解析结果不可用**：规则解析只覆盖 5 个字段，学历/工作/项目/求职意向/自评**全空** → AI 是**实质依赖**而非增强
3. **抽取质量本身有结构性缺陷**：PDF 未按位置排序（双栏乱序）、DOCX 表格被拍平 → 无论用 AI 还是规则，喂进去的文本就是脏的
4. **异步任务框架的落库边界不清**：Handler 私自写库（`resume_parse` 内部 insert 简历），框架无法补偿 → 这是问题 1 中脏数据的**根因**

## 2. 代码现状（基线事实）

### 2.1 现有链路

```
POST /portal/interview/resume/user/parse  (multipart)
        │
        ├─① extractText()  【纯 Java】PDFBox / POI / 手写编码探测
        │        └─ ⚠️ PDFTextStripper 未 setSortByPosition → 双栏乱序
        │        └─ ⚠️ XWPFWordExtractor 把表格拍平 → 行结构丢失
        │
        ├─② 结构化提取  【AI 优先】
        │        ├─ parseByLlm()   → 覆盖 10 字段
        │        └─ parseByRule()  → 异常时回退，仅覆盖 5 字段（60 行）
        │
        └─③ 落库 portal_user_resume
```

**关键事实：文本抽取（①）本来就是纯 Java 的，AI 只负责 ②。**

### 2.2 `parseByRule()` 的真实能力（远低于预期）

| 字段 | 现有规则能力 |
|---|---|
| 邮箱 | ✅ 正则 |
| 手机 | ✅ 正则 |
| 出生日期 | ✅ 正则（年 ≥ 1940） |
| 姓名 | ⚠️ 启发式：首个 2-4 字纯中文行 |
| 技能 | ⚠️ **硬编码 17 个关键词**，命中即标"了解" |
| 性别 / 求职意向 / 学历 / 工作 / 项目 / 自评 | ❌ **完全没有** |

→ AI 不可用时，仍会"解析成功"并建记录，但得到一条**只有邮箱+手机+姓名的空壳简历**。

### 2.3 在线表单的目标形状（抽取的落点）

`UserResumeVO` 与库表 `portal_user_resume` **完全同构**，四大类 + 每类「名称 / 起止时间 / 内容」：

```
portal_user_resume
├─ 基本信息   name, gender, birth_date, phone, email, avatar
├─ 求职意向   job_intention        (text/JSON: position, city, salaryMin, salaryMax, jobType, availableTime)
├─ 教育背景   educations           (text/JSON: school, major, degree, startDate, endDate, description)
├─ 工作经历   works                (text/JSON: company, position, startDate, endDate, description)
├─ 项目经历   projects             (text/JSON: name, role, startDate, endDate, description, url)
├─ 技能       skills               (text/JSON: name, level, category)
├─ 自我评价   self_intro
└─ 全文       full_text  mediumtext   ← 面试/匹配链路的实际输入
```

> **重要**：`self_intro` 是 `text`，其余条目类是 **`text` 存 JSON 数组** —— 即"结构化"本质是**把文本切成条目并序列化**，不改表结构即可落地。

### 2.4 面试链路实际消费的是什么（决定性事实）

`ResumeJobMatchService` L121-122：

```java
String resumeContent = (resume.getFullText() != null && !resume.getFullText().isBlank())
        ? resume.getFullText()          // ← 用的是【原文】
        : ...(才拼结构化字段);
```

结构化字段仅被用于**完整性判断**（L171-174：判断某类是否为空）。
→ **面试链路早就是"原文优先"**，并不依赖抽取出来的结构化字段。

## 3. 两个场景的容错性完全不同（本方案的核心拆分）

| | **场景 A：上传 → 填充在线表单** | **场景 B：面试准备 → 传给 AI 作上下文** |
|---|---|---|
| 消费者 | **人**（用户校对） | **AI**（无人校对） |
| 是否需要结构化 | ✅ **必须**（表单要各字段） | ❌ **不需要**（原文信息量更大） |
| 容错性 | ✅ 错了能改 | ❌ 错了没人知道 |
| 真正的要求 | **结构对 + 内容全** | **原文完整 + 不丢信息** |

### 结论（重要）

> **场景 B 应当直接喂 `fullText` 原文，不做结构化。**
>
> 理由：结构化是**有损压缩**，会丢掉项目难点、技术选型取舍等语义细节 —— 而这些恰是面试追问最需要的。
> 现状代码已经是"原文优先"，**场景 B 几乎无需改造**，只需保证 `fullText` 在任何路径下都**一定有值**。

→ **本方案的全部改造量集中在场景 A。**

## 4. 为什么"正则难以处理"：问题定性

**失败原因不是"正则不够强"，而是问题类型不同。**

| 简历里真实存在的情况 | 正则为何必然失败 |
|---|---|
| 公司名跨行 / 职位与公司同行 / 学校专业混排 | 正则没有行与列的空间概念 |
| `2019-2022 在阿里做后端` vs `阿里巴巴 2019.3-2022.6 高级工程师` | 语序不固定，字段位置无约定 |
| 「负责订单系统重构」 | **没有模式**，是自然语言，只能靠语义理解 |
| PDF 双栏 → 抽取后文字交错 | **文本层就已经乱了**，正则再强也救不回来 |

**业内共识**：简历解析 = **版面分析（Layout Analysis）** + **语义标注（Semantic Labeling）**。
正则只能做**最后一公里的字段清洗**（手机号、日期格式规范化），做不了主体。

## 5. 准确性标准：按"大类 + 条目"而非"字段完美"

用户已明确目标（原始表述）：

> 「我也不追求 100%。就是基本的信息提取，即使是能按大类分析也可以：
> 基本信息（姓名、邮箱…）、教育背景、项目经历（1、2、3：名称、起始时间、内容）、
> 工作经历（1、2、3：分别有起始时间：内容）」

**这个标准与表单形状天然对齐**，且**把问题从"语义理解"降级为"分桶 + 切段"**：

| 维度 | 完美主义（做不到，且不需要） | **本方案标准（做得到）** |
|---|---|---|
| 工作要求 | 精确切分技术栈/成果/难点 | **整段原文塞进 `description`** |
| 项目要求 | 推断 `role`、技术标签 | `name` + 时间对了即合格，`role` 留空 |
| 学历要求 | 判断 985/211、GPA 换算 | `school` + `degree` + 时间 |
| 准确率目标 | 字段级 95%+ | **结构正确**：归对大类 + 切对条目 |

**→ 本质是"分桶 + 切段"，确定性远高于语义抽取。**

## 6. 业界做法（客观陈述）

| 路线 | 代表 | 准确率 | 成本 | 适用性 |
|---|---|---|---|---|
| **A. 模板化/固定版面** | 招聘网站自研表单 | ~95% | 低 | ❌ **不适用**：用户自由上传，**无法控制格式** |
| **B. 规则 + 版面分析** | 早期 CV 解析引擎（Sovren 等） | 70~85% | 低 | ✅ 中文标签型简历可行 |
| **C. 云 API（专用简历解析）** | 阿里云/腾讯云/百度 AI、HireEZ、Daxtra | 92~97% | 按次计费 | 高准确率但引入外部依赖与成本 |
| **D. LLM 抽取** | GPT/Claude/DeepSeek + JSON Schema | 90~95% | 每次一次调用 | 当前事实标准，但有幻觉与不稳定 |

**2024-2026 主流是混合管线**，且业界普遍采用最后一步：

```
版面修复 → LLM 结构化（带 Schema）→ 置信度 → 【人工校对页（高亮低置信）】
```

**关键共识：没有人追求全自动 100%，而是追求「人工校对成本最低」。**
因为下游本来就是**人**（编辑表单）或**能容忍模糊的 AI**（面试上下文），不是资金交易。

## 7. 方案：渐进式三阶段（按最小需求起步）

> **核心原则**：**先保证"读得出来、分得对大类、原文不丢"，再逐步细化字段。**
> 宁可 Phase 1 字段填得少，也**绝不能丢内容**。

### Phase 1 ⭐ 大类划分 + 排版保真（**最小需求，先做这个**）

**目标**：把简历切成大类，**每类内容完整保留原文**，不做字段猜测。

| # | 内容 |
|---|---|
| 1.1 | **修文本抽取质量**：PDF 开 `setSortByPosition(true)`；DOCX 改遍历 body elements，**表格单元格用 `\t` 连成行**（不再拍平） |
| 1.2 | **章节标题词典** → 识别大类：基本信息 / 求职意向 / 教育背景 / 工作经历 / 项目经历 / 技能 / 自我评价 / 其他 |
| 1.3 | **按大类切块**，每块**原文整段保留**（含未识别大类，进"其他"，**不丢**） |
| 1.4 | **基本信息**（高置信、低风险）：手机 / 邮箱 / 姓名 / 性别 / 出生日期 |
| 1.5 | `full_text` 保证**一定有值**（任何路径都写） |
| 1.6 | **反显到表单**：大类块内容落到对应字段的 `description`；字段抽不准就留空 |

**Phase 1 的产出示例**：

```
educations = [ { school:"", major:"", degree:"", startDate:"", endDate:"",
                 description:"北京大学 计算机科学与技术 2016.09-2020.06 本科\n主修课程：..." } ]
```
> 即：**即使字段没抽出来，整段内容也在 `description` 里**，用户只需"挪一挪"，而不是"重新打一遍"。

**Phase 1 验收标准**：任意格式简历 → 大类分对 + 内容零丢失 + 基本信息抽对。

### Phase 2 条目化（1、2、3）

**目标**：在大类内按日期锚点切成条目，填「名称 / 起止时间 / 内容」。

| # | 内容 |
|---|---|
| 2.1 | **日期范围解析器**：`2020.03-2023.06`、`2020年3月至今`、`2020/03—2023/06`、`2020-2023` → `(startDate, endDate, isCurrent)` |
| 2.2 | **条目切分**：日期行 = 条目锚点；下一条日期行或下一章节头 = 终点 |
| 2.3 | **字段分配**：日期行**上方紧邻非空行** → `school`/`company`/`name`；剩余文本 → `description`（原样保留） |
| 2.4 | `degree` 词典匹配（博士/硕士/研究生/本科/学士/大专/专科） |
| 2.5 | **技能词域零硬编码**：聚合 `portal_job_template.required_skills`（5 条岗位已有 40~60 词）+ `portal_tag`(38 行) |
| 2.6 | `job_intention.position`：用岗位模板名（`portal_job_template.name`）匹配 |
| 2.7 | 派生：由工作经历日期区间计算**工作年限** |

**Phase 2 预期结构正确率**（诚实估计）：

| 大类 | 结构正确率 | 关键字段表现 |
|---|---|---|
| 基本信息 | — | 手机/邮箱 ~98%、姓名 ~85%、性别 ~95%（仅显式标签） |
| 自我评价 | **~90%** | 整块取，几乎不会错 |
| 教育背景 | **~90%** | 学校 ~85%、起止时间 ~90%、学历 ~85% |
| 工作经历 | **~85%** | 公司 ~80%、起止时间 ~90%、职位 ~70% |
| 项目经历 | **~80%** | 名称 ~75%、起止时间 ~85%、内容原样保留 |
| 技能 | **~85%** | 词域匹配 |

→ **换算成产品指标**：一份规范简历约需用户改 **2~4 个字段**。

### Phase 3 可选：AI 增强（**不是必需依赖**）

- 触发条件：规则路径**字段缺失过多** 或 **明确低置信**
- 作用：补 Phase 2 抽不到的语义类内容
- **硬要求**：AI 不可用时，Phase 1+2 的结果**必须自身可用**（当前不满足，这是要修的核心）
- 顺带：AI 调用量大幅下降 → 成本与延迟双降

## 8. 规则设计详解（Phase 1+2 的 6 条规则）

### R0 文本预处理（**必须先做，否则后面全废**）
| 修正 | 原因 |
|---|---|
| `PDFTextStripper.setSortByPosition(true)` | 双栏简历现在**文字交错**，分桶必崩 |
| DOCX 遍历 body elements，表格单元格 `\t` 连接 | 现在表格被拍平，**行结构丢失** |
| 按 `\n` 切行、去零宽字符、全角空格归一 | 统一后续匹配口径 |

### R1 章节标题词典 → 分桶
| 目标桶 | 同义词（首批） |
|---|---|
| `basic` | 基本信息、个人信息、个人资料 |
| `intention` | 求职意向、求职目标、职业意向、期望职位 |
| `edu` | 教育背景、教育经历、学习经历、教育信息 |
| `work` | 工作经历、工作经验、职业经历、实习经历 |
| `project` | 项目经历、项目经验、项目实践 |
| `skill` | 专业技能、技能特长、技能清单、掌握技能 |
| `self` | 自我评价、个人评价、自我介绍、个人简介 |
| `other` | 荣誉奖项、证书、校园经历…（**不解析但保留原文**） |

> 词典建议放常量类，后续可迁 `sys_dict_data` 支持后台维护（避免写死）。

### R2 日期范围解析器 → 切条目 + 算时长
输入形态：`2020.03-2023.06` / `2020年3月至今` / `2020/03—2023/06` / `2020-2023` / `2020.03 – 2023.06`
输出：`(startDate, endDate, isCurrent)` —— **正好是表单字段类型（String），无需转换**

### R3 条目切分器 → 得到 1、2、3
在 `edu` / `work` / `project` 桶内：
```
日期行  = 条目起点（锚点）
下一条日期行 或 下一章节标题 = 条目终点
```

### R4 条目内字段分配 → 名称 / 时间 / 内容
| 表单字段 | 取法 | 可靠性 |
|---|---|---|
| `startDate` / `endDate` | R2 结果 | ✅ 高 |
| `school` / `company` / `name` | **日期行上方紧邻非空行** | ⚠️ 中 |
| `major` / `position` / `role` | 标题行按分隔符（空格 `|` `·` `-`）切两段 → 第二段；**切不出留空** | ⚠️ 中低 |
| `degree` | 词典匹配 | ⚠️ 中 |
| `description` | **条目块剩余全部文本原样保留** | ✅ 高 |

### R5 基本信息抽取（增强 `parseByRule`）
| 字段 | 规则 |
|---|---|
| `phone` / `email` | 已有正则 ✅（需排除身份证/QQ 干扰） |
| `name` | 优先「姓名：」显式标签；否则**前 5 行内**首个 2-4 字纯中文且非章节词 |
| `gender` | **只认显式标签**（「性别：男」或 `男 | 28岁`），**绝不从上下文推断** |
| `birthDate` | 已有正则；需排除「入学年月」误抓 |
| `jobIntention.position` | `intention` 桶内匹配 `portal_job_template.name` + 常见岗位词 |
| `selfIntro` | `self` 桶**整块直接取** |

### R6 技能抽取 → 零硬编码
聚合 `portal_job_template.required_skills`（JSON 数组）+ `portal_tag.name` 作为词域，全文匹配。
> **不新增一份写死的技能词典** —— 复用已治理过的岗位配置数据。

## 9. 两条贯穿全程的铁设计原则

### 原则 1：内容永不丢失
即使 `school` / `company` 没抽出来，**整段原文必须进 `description`**。
> 最坏情况是"用户手动把公司名从描述挪到公司框"，**而不是内容消失**。

### 原则 2：宁缺勿错（防静默错误）
抽不准的字段**留空，不要猜**。
- 空值 → 用户会补
- **错值 → 用户会信** ← 真正的伤害

> 唯一例外：`description` 允许"多"，不允许"错"（多出的内容用户删掉即可）。

## 10. 准确性的真正保障在 UI（业界共通做法）

算法提不上去的部分，靠**"让错误可见"**兜底。成本递增：

| # | 手段 | 效果 |
|---|---|---|
| **U1** ⭐ | **左右对照**：左原文（按章节高亮命中处），右填好的表单 | 用户扫一眼即知对错，**性价比最高** |
| **U2** | **字段级置信度标记**：低置信打「⚠️ 待确认」，不阻断 | 注意力导向真正可疑处 |
| **U3** | 低置信字段**宁可不填**（留空 + 占位提示），而非填可能错的值 | 防"静默错误" |

> **U3 反直觉但最关键**：错的值比空的值危害大得多 —— 空值用户会补，错值用户会信。

### 重新定义"准确性"指标（本方案的核心主张）

**不要用"字段提取准确率 95%"当目标**（无法达成也无法验证）。改为：

> **「用户从上传到确认表单完成，需要修改几个字段 / 花多少秒」**

- 平均改 3 个字段、20 秒 → **成功**（比手填 5 分钟快 15 倍）
- 平均改 15 个字段 → 失败（不如手填）

**该指标可测、可优化，并直接推导出产品形态**：
> 上传后**立即**显示"预填草稿"，而不是"等 AI 解析完"。

## 11. 硬限制（诚实声明）

| 限制 | 说明 | 应对 |
|---|---|---|
| **扫描件 / 图片型 PDF** | **无文本层**，纯 Java 与 LLM 都读不到 | 必须 OCR（Tesseract/PaddleOCR）；建议**显式提示用户"请上传文本版简历"** |
| **PDF 双栏 / 表格** | 抽取后文字交错 | Phase 1.1 修复（**纯 Java，成本极低**） |
| **LLM 幻觉** | 可能编造公司名/时间 | U1 左右对照使人可发现；**不做"全自动入库不给人看"** |
| **LLM 输出不稳定** | 同输入两次结果不同 | 规则做底座保证下限，LLM 仅作增强 |
| **PDF 中投递平台水印广告** | 干扰文本 | 预处理阶段过滤常见平台水印行 |

## 13. 关于命名与框架重构（本轮评估结论，供决策留痕）

| 议题 | 结论 | 依据 |
|---|---|---|
| `portal_ai_task` 表改名 | ⏳ **推迟** | ① **零功能收益**：它本就是通用队列，限制复用的是 `user_id NOT NULL` 与缺 `idempotency_key`，**与名字无关**；② 项目已有同款先例 `sys_audit_task`（跨 8+ 服务共用的通用任务表，名字同样带遗留色彩，一直可用）；③ **改名不可逆地破坏可搜索性**：历史增量脚本按铁律不可改，`git log`/旧日志全叫旧名；④ `RENAME TABLE` 是**元数据操作**，未来表再大也是毫秒级 → **"趁数据少"不构成理由** |
| `AiTaskHandler` 迁包 / 类改名 | ⏳ **推迟** | 与上条同因；且**只改类名会造成表名/类名新的不一致**。正确触发条件是：**真正出现非 AI 长任务消费者**，届时与能力补齐一起做，边际成本最低 |
| 框架能力补齐（幂等键 / 原子抢占 / 重试 / `user_id` 可空） | ⏳ **独立批次** | 补 `user_id` 可空才是"全局复用"的**真前提**（当前系统发起的任务写不进来） |
| 修正上轮结论 | ❌ 我此前称"改名成本几乎为零"是**错的**：漏算了实体类 `PortalAiTask` 的 **27 处代码引用**（0 处注释） |

## 14. `AiTaskHandler` 体系评估（四 Handler 横向分析）

### 14.1 全景对比

| | `resume_parse` | `job_match` | `deep_optimize` | `ai_draft` |
|---|---|---|---|---|
| **输入来源** | **客户端上传内容**（payload） | 服务端已有资源 | 服务端已有资源 | 服务端已有资源 |
| **依赖前置** | ❌ 无（自己造简历） | ✅ 需简历已存在 | ✅ 需简历已存在 | ✅ 需简历已存在 |
| **用 payload** | ✅ 唯一 | ❌ | ❌ | ❌ |
| **归属校验** | 无（按 userId 建新行，**正确**） | ✅ 显式查 | ✅ 显式查 | ❌ **无（越权缺口）** |
| **失败语义** | 抛异常 | 抛异常 | 抛异常 | ⚠️ **返回空结果 = 假成功** |
| **落库职责** | ⚠️ **Handler 内部 insert** | 业务层落报告 | 纯返回 VO | 纯返回 Map |

### 14.2 核心判断

> **这 4 个 Handler 不是"同一框架的 4 个实现"，而是「1 个入口型 + 3 个派发型」被塞进了同一个接口。**
> 重复的 8 行取值/校验样板、3 种失败语义、落库边界不清，都是这个错配的症状。

### 14.3 问题清单

| # | 问题 | 严重度 |
|---|---|---|
| P1 | 接口过宽：`payload` 只有入口型用，派发型永远传 null | 🔴 |
| P2 | 4 处重复拆参 + 校验（措辞还不一致），框架缺**参数声明**能力 | 🔴 |
| P3 | **归属校验放错层**：应属业务服务职责；放 Handler 导致**漏一个就是越权**（`ai_draft` 即活例），且 `job_match` 存在**双重校验** | 🔴 |
| P4 | **3 种失败语义**：`ai_draft` 返回空结果被记为 `success`（假成功），前端无法区分"没内容"与"失败" | 🔴 |
| P5 | **落库边界不清**：Handler 私自写库 → **框架无从补偿** → **这是原始脏数据 bug 的根因** | 🔴 |
| P6 | `ResumeParseVO` 缺 `@JsonIgnoreProperties(ignoreUnknown=true)`，结果 JSON 回读存在前向兼容风险 | 🟠 |
| P7 | `resume_parse` 不做归属校验是**对的**，但未注释说明，后人可能"补上"一个错误校验 | 🟠 |

### 14.4 建议（分层）

**立刻可做（零风险）**
1. `ai_draft` 的"假成功"改为显式失败（或结果内标 `degraded:true`）
2. `ai_draft` 补齐归属校验（交给业务服务内部做）
3. 4 个 Handler 注释补齐「输入类型 / 是否写库 / 失败语义」三行声明

**待 `resume_parse` 重构后再评**
4. 框架加参数 Schema 声明（若入口型消失，需求弱化）
5. **统一落库边界**（Handler 只返回，由框架/调用方在成功后落库）—— 这是**根治 P5** 的修法
6. 迁包 / 改名 / 表改名
