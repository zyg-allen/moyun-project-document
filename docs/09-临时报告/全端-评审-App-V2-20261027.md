# 记账 App 复评（V2）：页面 · 接口 · 体验 · 幂等 · 安全 · 整体设计

> 复评日期：2026-10-27
> 对照：V1（6.8/10，2026-10-27）
> 方式：代码静态审查 + 指标采样 + 466 条测试结果

---

## 一、总评：7.2 / 10（V1 为 6.8）

| 维度 | V1 | V2 | 变化 | 依据 |
|---|---|---|---|---|
| 页面与视觉 | 7.0 | 7.2 | +0.2 | 消息入口/角标、弹层层级、存钱页重构 |
| 交互与体验 | 6.5 | 6.8 | +0.3 | 失败态+重试、列表解析统一、操作区上移 |
| 接口设计 | 6.0 | 7.3 | **+1.3** | 6 个模块 VO 化、8 个契约测试、统一 listOf |
| 幂等性 | 7.0 | 7.6 | +0.6 | 存钱 7 个写接口加防重+限流 |
| 安全性 | 7.5 | 7.6 | +0.1 | 防护注解增加；限流/校验覆盖仍低 |
| 整体架构 | 6.5 | 6.9 | +0.4 | 可观测性、接口清单、死代码清理 |
| 生产就绪 | 6.0 | 7.0 | **+1.0** | traceId、慢接口、零调用报告、统计页 |

**一句话**：从“功能跑得快、契约补得慢”，变成了“契约与可观测性开始成体系”；但**接口规模与防护覆盖**仍是最大短板。

## 三、页面与体验

### 改善

1. 消息中心：入口强制保留、未读角标、失败态+重试；
2. 弹层层级统一到 2000，修复二级分类被 TabBar 遮挡；
3. 存钱详情：从列表改为周视图 + 年份分隔 + 选中放大显示日期；
4. 操作区上移，长列表不再需要滚到底；
5. 全局列表解析 `listOf()`，消除“假空态”。

### 仍存在

| 级别 | 问题 |
|---|---|
| P1 | 空态/骨架覆盖不均（仅 4 处骨架屏） |
| P1 | 表单校验仍以 toast 为主，无字段级提示 |
| P2 | 深色下小字号（16~18rpx）对比度偏低 |
| P2 | 部分页面信息重复（已修存钱，其他页未系统排查） |

---

## 四、接口设计

### 改善

- 6 个模块 VO 化：存钱列表/详情、流水列表、资产列表、商品列表、消息列表；
- 8 个契约测试锁定字段与“不外泄”；
- 删除旧 `/deposit`、`/fail` 与 5 个死 API 封装；
- 新增响应解析工具，前端不再手写 `records || []`。

### 仍存在

| 级别 | 问题 |
|---|---|
| P0 | **977 个接口 vs 33 个页面**，接口规模远超产品面 |
| P1 | 限流覆盖 2.1%，登录/验证码/AI/导出仍缺频控 |
| P1 | `@Valid` 覆盖 7.8%，大量接口靠手写 if |
| P1 | 报表/首页仍是 Map（已用注释与契约测试兜底，属可接受债务） |
| P2 | 无 `/v1` 版本化；401 仍返回 HTTP 200 |

---

## 五、幂等性

### 改善

- 存钱 7 个写接口：`@RepeatSubmit(3s)` + `@RateLimiter(60/60)`；
- 转账/存入沿用 `client_uuid` + 唯一索引；
- 前端 26 个页面提交锁。

### 仍存在

| 风险 | 说明 |
|---|---|
| 覆盖不足 | 21 个防重注解 / 977 接口 |
| 状态竞态 | mark/link 无行锁，并发可能互相覆盖 |
| 批量/导入/上传 | 无幂等键 |
| AI 调用 | 重试可能重复计费 |

---

## 六、安全性

### 保持良好

- JWT 双密钥 + audience；生产端点硬拦截；CORS 生产 fail-closed；
- 核心服务按 userId 校验归属；
- 数据授权、审计、脱敏、协议留痕齐备。

### 仍存在

| 级别 | 风险 |
|---|---|
| P0 | 限流覆盖低（2.1%） |
| P1 | 入参校验覆盖低（7.8%） |
| P1 | 文件上传类型/大小校验分散 |
| P2 | H5 token 存 localStorage；错误信息可能直出 |

---

## 七、整体架构与可观测性

### 改善

- `TraceIdFilter`：`X-Trace-Id` 贯穿日志，慢接口 >500ms 告警；
- `ApiStatsFilter` + `ApiCatalog`：按 URI 计数、启动时收集接口清单；
- `/cms/monitor/api-stats` 与 `/zero-call` + 后台页面；
- 每日 09:30 零调用报告落文件。

### 仍存在

- 无 Prometheus/指标导出，统计仅内存、重启清零；
- 无告警通道（慢接口只写日志）；
- 无 E2E 主流程测试；
- 单机部署，数据库/缓存/对象存储同机。

---

## 八、下一步优先级

### P0（继续收敛）

1. 敏感接口限流补齐（登录、验证码、AI、导出）；
2. `@Valid` 覆盖到所有写接口 DTO；
3. 接口下线：按零调用报告连续 7 天为 0 的批量标记 `@Deprecated`。

### P1

1. 报表 `financial` 契约测试；
2. 主流程 E2E（记一笔、转账、存钱、消息）；
3. 指标导出（Micrometer → Prometheus）与慢接口告警。

### P2

1. Map 接口（首页/报表）逐步类型化；
2. 前端骨架屏与字段级校验；
3. 单机 → 数据库/对象存储独立。

---

## 九、结论

**单点能力 8 分，系统化 7 分，综合 7.2。**
这轮最大的价值不是多了几个 VO，而是建立了三件事：**契约测试、调用统计、链路追踪**。它们会让后续每次改接口都可验证、可追踪、可下线。

下一步若只能做一件事：**把限流和入参校验补到所有写接口**，这是当前最明显的生产风险。
