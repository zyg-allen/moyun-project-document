# 记账 App 客观评审：页面 · 接口 · 体验 · 幂等 · 安全 · 整体设计

> 评审日期：2026-10-27
> 评审方式：代码静态审查 + 本会话真实故障复盘 + 已有压测/构建数据
> 范围：`moyun-ledger-app`（33 页）、`moyun-server`（174 个 Controller / 978 个接口）
> 结论先行：**工程完成度高于多数单人项目，但"生产级"还差一层统一契约与防护**。综合 **6.8 / 10**。

## 二、页面与体验

### 做得好的

1. **统一骨架**：`NavBar` + 主题变量（`--card/--text-main/--primary`）+ 安全区适配，暗色/护眼可切换；
2. **组件复用**：`PickerSheet / PickerWheel / CalendarPicker / SkeletonList / KeyboardAwareSheet`，替代原生 picker 后暗色下不再白屏；
3. **空态覆盖广**：139 处 `empty/暂无` 文案，基本每个列表都有兜底；
4. **提交锁**：26 个页面使用 `submitLock`，避免双击重复提交；
5. **金额规范**：`utils/money` 统一元/分转换、千分位、输入净化。

### 主要问题（按严重度）

| 级别 | 问题 | 证据/现象 |
|---|---|---|
| P0 | **弹层层级不稳定** | 二级分类弹层被 TabBar 盖住，名称整体不可见（本次已修：z-index 900→2000） |
| P0 | **信息重复** | 存钱详情同一期出现 3 次（头部/提示卡/网格/操作卡），用户明确反馈"元素重复" |
| P1 | **弹窗堆叠被吞** | ActionSheet 内再开 ActionSheet，部分平台直接无响应（已加 200ms 延迟规避） |
| P1 | **页面加载态缺失** | 仅 4 处骨架屏，其余是"加载中…"文字或空白，列表页首屏体验一般 |
| P1 | **错误提示碎片化** | 有的 catch 静默、有的 toast、有的依赖拦截器；用户无法判断"是没数据还是失败" |
| P2 | **长页面操作区位置** | 52 周 52 格时操作按钮在底部，需要长滚动（已把操作卡上移解决） |
| P2 | **深色对比度** | 次级文字 `--text-muted` 在部分背景上偏低，小字号（16~18rpx）可读性弱 |

### 体验建议

- 建立**全局弹层管理器**（同一时刻只允许一个 sheet，层级统一 2000+，TabBar 之上）；
- 列表统一三态：`loading 骨架 / empty 插画+行动按钮 / error 重试`；
- 表单校验从 toast 改为**字段内联提示**（金额、账户、必填）；
- 金额输入统一千分位与两位小数，提交前展示确认摘要。

## 三、接口设计

### 现状数据

| 指标 | 数值 |
|---|---|
| Controller | 174 |
| 接口 | 978 |
| `@Valid/@Validated` | 76 处 |
| 限流注解 `@RateLimiter` | 15 处 |
| 防重注解 `@RepeatSubmit` | 16 处 |
| 幂等键 `clientUuid` | 18 处 |

### 问题

1. **返回结构不统一（P0）**
   - `/portal/ledger/assets` 返回 `{records,total}`，其他列表有的直接返回数组；
   - 前端按数组取 `.length` 导致"暂无资产账户"假空态（真实故障）。
   - 建议统一 `{code,msg,data:{records,total,pageNum,pageSize}}`，或统一数组 + 分页头。

2. **同一能力多套接口（P1）**
   - 存钱：`/deposit`、`/fail` 与新的 `/mark`、`/link`、`/transfer` 并存；
   - 前端已不用旧接口，后端仍保留，文档与权限点容易错乱。

3. **实体直出（P1）**
   - 多处 Controller 直接返回 Entity（`LedgerSavingPlan`、`LedgerTransaction`），字段增减即破坏前端契约，且容易泄露内部字段。

4. **命名不一致（P2）**
   - 后端 `/savings`，前端叫 `saving-plans`；`asset` / `assets` / `account` 混用。

5. **错误语义（P1）**
   - 业务失败统一 HTTP 200 + `code!=200`，网关/监控无法按状态码告警；
   - 401 也返回 200，需前端解析 body，第三方接入不友好。

6. **版本化缺失（P2）**
   - 978 个接口无 `/v1` 前缀，客户端无法灰度。

### 建议

- 先做**统一响应包装 + 分页 DTO**（1~2 天，收益最大）；
- 旧接口标记 `@Deprecated` 并设下线日期；
- 对外接口（App/小程序）走 VO，禁止 Entity 直出。

## 四、幂等性

### 做得好的

- 转账/存入用 `client_uuid = saving:{recordId}`，数据库唯一索引兜底；
- `ledger_saving_record.uk_record_txn` 防止一条流水关联多期；
- 26 个页面提交锁、16 处 `@RepeatSubmit`；
- 存钱标记接口天然幂等（重复标记只更新同一条记录）。

### 不足

| 风险 | 说明 |
|---|---|
| 覆盖不均 | 978 个接口里仅 18 处显式幂等键、16 处防重 |
| 状态竞态 | `mark/link/unlink` 先查后改，无行锁/乐观锁，并发下可能互相覆盖 |
| 双击创建计划 | 依赖前端锁，接口层无幂等（重复提交会生成两个计划） |
| 文件/导入 | 上传、批量导入无幂等键，重试会产生重复数据 |
| AI 调用 | 流式/工具调用重试可能重复计费，无请求级幂等 |
| 重试语义 | 前端网络重试无统一策略，POST 重试可能重复写 |

### 建议

- 抽象 `@Idempotent(key)` 注解 + Redis SETNX（覆盖所有 POST/PUT 写接口）；
- 关键更新加 `version` 乐观锁或 `SELECT ... FOR UPDATE`；
- 文件上传用内容 hash 去重。

## 五、安全性

### 做得好的

1. **JWT 双密钥 + audience**：管理端与门户端隔离，防令牌串用；
2. **越权防护**：核心服务按 `userId` 校验归属（Ledger 模块 25 处）；
3. **生产加固**：`@Profile("prod")` 拦截 Druid/Knife4j；启动配置校验 15/15；CORS 生产 fail-closed；
4. **合规**：数据授权、访问审计、脱敏、协议留痕；
5. **日志**：关键操作有审计日志。

### 风险

| 级别 | 风险 | 说明 |
|---|---|---|
| P0 | 限流覆盖仅 1.5% | 15/978，登录、短信、AI、导出等敏感接口缺少频控 |
| P0 | 参数校验不足 | 76 处 `@Valid`，大量接口靠手写 if，边界值/长度/枚举易漏 |
| P1 | 文件上传校验 | 类型、大小、内容嗅探需统一（当前分散在各 Controller） |
| P1 | 富文本/XSS | 门户文章、反馈内容若直出需转义 |
| P1 | 令牌存储 | H5 存 localStorage，XSS 即可窃取；建议短期 token + HttpOnly 刷新 |
| P2 | 错误信息 | 部分异常直接把后端信息返回给前端 |
| P2 | 第三方回调 | 微信/支付回调的签名校验需逐项确认 |

### 建议

- 登录/验证码/导出/AI 接口**强制限流**；
- DTO 全量加 `@NotBlank/@Size/@DecimalMin`，Controller 统一 `@Valid`；
- 上传统一走 `FileValidator`（白名单 + 大小 + magic number）。

## 六、整体设计

### 合理之处

- 模块化单体 + 分层（Controller-Service-Mapper）适合单人维护；
- 记账、库存、门户、AI 中台按包边界拆分，预留了服务化可能；
- SQL 双轨、配置外置、启动校验，工程规范意识强。

### 需要正视

1. **功能面 > 验证阶段所需**
   33 个页面配 978 个接口，AI 中台（Agent/工作流/RAG）占了大量复杂度，但核心记账闭环的体验问题仍在反复修。
2. **领域模型偏贫血**
   Entity 同时承担持久化与接口出参，领域规则散落在 Service 的大方法里。
3. **可观测性不足**
   有日志无 traceId 贯穿、无接口耗时指标、无错误率看板；出问题只能翻日志。
4. **测试结构**
   单元/守卫测试有，但缺少**契约测试**（前后端返回结构）与**端到端主流程测试**，本次多个 bug 都属于契约/层级问题。
5. **复杂度预算**
   单人项目应优先"少而稳"：先把记账主链路做到零故障，再扩 AI 场景。

## 七、优先级路线图

### P0（1~2 周，直接影响可用性）

1. 统一响应结构与分页契约（消灭"假空态"类 bug）；
2. 弹层管理器（层级、互斥、TabBar 避让）；
3. 敏感接口限流（登录/验证码/AI/导出）；
4. 写接口幂等框架（注解 + Redis）；
5. 页面三态统一（loading/empty/error+重试）。

### P1（2~4 周）

1. Entity → VO 隔离；
2. 旧接口下线（deposit/fail）；
3. 上传校验统一；
4. traceId + 慢接口日志 + 错误率统计；
5. 主流程 E2E（记一笔、转账、存钱标记、关联流水）。

### P2（持续）

1. API 版本化；
2. 领域模型重构（记账/存钱/库存边界）；
3. 前端骨架屏与可访问性；
4. 复杂度瘦身：AI 场景按使用率收敛。

## 八、客观点评

**优点**：这不是"Demo 级"项目。认证隔离、生产配置校验、SQL 双轨、守卫测试、成本计量这些点，很多工作 3~5 年的开发者不会主动做。

**短板**：典型"功能跑得快、契约与防护补得慢"。本次连续出现的假空态、弹层遮挡、重复渲染、字面量转义，本质都是**缺少统一契约与全局 UI 基础设施**，而不是单点技术能力问题。

**一句话**：**单点能力 8 分，系统化 6 分**。把"统一响应、统一弹层、统一幂等、统一三态"这四件事做完，整体会从 6.8 到 8 分以上。
