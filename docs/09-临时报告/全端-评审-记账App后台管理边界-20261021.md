# 全端-评审-记账 App 后台管理边界（审计 + 整改方案）

> **版本** v1.1 · 2026-10-21（v1.0 审计 + §10 可行性复核与 3 处口径修正）
> **审计对象**：`moyun-ledger-app`（uni-app 小程序/H5）、`moyun-server` 记账模块（`com.moyun.ledger`）、`moyun-admin-vue` 记账后台（`views/cms/ledger`）
> **口径**：一切以代码为准。本文每条「现状」都附文件行号，「应然」均为可落地改造项。
> **定位**：阶段性评审报告（非规范）。实施后按规范四同步：devlog / README / 方案文档 / 部署指南。

## 0 结论速览

1. **后台只覆盖了记账 App 的 5 个面**：预设分类、功能入口、运营统计、用户流水（脱敏）、2 个字典。
   系统预设共 21 项，现状是「1 项完整 + 3 项部分 + 17 项缺失」：**13 类下拉/枚举仍硬编码在两端代码里**，**3 张预设表（商品类目/售卖渠道/进货渠道）有数据但没有任何维护入口**，**1 张预设表（功能入口）后台只能改 4 个字段、不能增删**。
   → 改一个下拉选项、加一个渠道，今天都必须发版 + 跑 SQL。
2. **用户数据当前是「未授权即可见」**：后台「用户管理」可直接查任意用户流水（类型/金额/分类/日期）；`cms/user` 还能看到**明文手机号/邮箱/画像**。
   按本次确定的规则（*获得用户授权才可查看，否则保密*），**这条现状即不合规**，是本次唯一 P0 红线。
3. **后台看用户数据零审计**：4 个 `CmsLedger*` Controller **全部没有 `@Log`**，谁看了谁、什么时候看、为什么看，事后不可追溯。
4. **「后台管 App」链路本身有 3 个真实缺陷**：隐藏功能不生效（前端兜底把隐藏项又加回来）、「赞赏」入口配置为可见但无路由（点了没反应）、流水状态标签反了（有效显示「已删」）。
5. **注销与删除权未闭环**：App 内没有注销入口；注销只改 `del_flag`，记账数据永久保留；App 内无隐私政策、注册无协议勾选。
6. **边界建议按三档 + 一禁区**：A 系统预设（必须后台管）/ B 运营参数（后台可调但需留痕）/ C 用户数据（默认保密，授权可见）/ **D 客户端表现（主题、图标集）不要纳入后台**——这是「适当管理」的另一半。

## 1 判定口径

### 1.1 三档定义

| 档位 | 定义 | 后台权限 | 合规要求 |
|---|---|---|---|
| **A 系统预设** | 平台提供的分类、字典、下拉候选，用户侧只读（用户可另建自己的） | 增删改查、排序、启停 | 变更留痕；被引用时禁删（只能停用） |
| **B 运营参数** | 影响 App 展示/行为但不属于用户内容的配置（入口显隐、角标、阈值、权重） | 可调 | 留痕 + 可回溯版本；不得改变已发生数据的统计口径 |
| **C 用户数据** | 用户自己产生的记账/资产/预算/库存/AI 报告及身份画像 | **默认不可见**；仅在用户授权 + 有限期限 + 明确用途下可读 | 单独同意、最小必要、访问审计、可撤回、到期失效 |
| **D 客户端表现** | 主题皮肤、emoji 图标集、文案、交互动效 | 不做后台 | 随版本发布 |

### 1.2 三条硬判定

- **可运营性**：一个值如果运营想改而必须发版，它就该进后台（A 或 B）。
- **最小必要**：后台能拿到的最细粒度应是「聚合指标」，个体数据必须额外授权（C）。
- **可追溯**：任何后台对用户数据的读取，都必须留痕（谁/何时/哪条/为什么）。

| 数据类别 | 敏感级别 | 后台当前可见性 | 应然 |
|---|---|---|---|

**判定口径落地**：C 档里只有「聚合指标」可以无条件看；「个体数据」一律走 §6 的授权链路。

### 3.4 D 档：不做后台（避免过度管理）

| 对象 | 理由 |
|---|---|
| 主题皮肤 5 套 + 外观 3 套（`stores/theme.js:9-113`） | 纯客户端表现层，涉及 CSS 变量，远程配置收益低、兼容风险高 |
| emoji 图标集（`utils/categoryIcon.js`） | 与前端渲染强耦合；后台只应选「已支持的 key」，不应自由输入 |
| 表单校验规则、文案 | 随版本发布；文案如需运营，走 CMS 文案表，不进记账后台 |
| 用户自建分类/渠道/类目/仓库/货架 | 属用户内容，后台**只读**；不提供改删（现状分类已如此，应推广到其余） |

## 5 问题清单

### P0（合规红线，必须修）

#### P0-1 个体数据「未授权即可见」

- **证据**：`CmsLedgerUserController.java:152-190` 查询任意 `userId` 的流水，无授权校验；`users/index.vue:37` 一键「查看流水」。
- **影响**：金融账户信息属《个人信息保护法》第 28 条敏感个人信息，第 29 条要求**单独同意**；内部人员无授权即可按用户检索，属「超出告知目的的处理」。
- **整改**：新增用户授权链路（§6.2），后台查询前 `assertAuthorized(userId, "transaction")`，未授权返回 403 +「用户未授权查看」；默认列表只显示聚合列。

#### P0-2 敏感数据访问无审计

- **证据**：4 个 `CmsLedger*` Controller 均无 `@Log`（对比 `CmsPortalUserController.java:80,91,102` 都有）。
- **影响**：《数据安全法》第 27 条要求全流程记录；出事后无法定位泄露源。
- **整改**：所有 C 档读取接口加 `@Log(title="记账-用户数据访问", businessType=OTHER)` + 专用 `sys_data_access_log`（含 `target_user_id`/`scope`/`auth_id`/`result`/IP）。

#### P0-3 注销不删除、App 无注销入口

- **证据**：`PortalUserController.java:303-325` 仅置 `del_flag=2, status=1`；App `pages.json` 无注销页，`settings` 页也无入口；`mine/forgot-password/index.vue:9` 明示「历史数据保留」。
- **影响**：违反第 47 条删除权；账号注销后记账数据永久留存，无保存期限说明。
- **整改**：App 设置页加「注销账号」→ 二次确认 + 告知删除范围；注销后 30 天冷静期结束**物理删除或不可逆匿名化**记账域全部数据（`ledger_*` 按 userId 清理，保留匿名化统计计数）；提供「导出后注销」路径。

#### P0-4 手机号/邮箱明文展示

- **证据**：`CmsPortalUserVO.java:43-47` 返回原始值；`cms/user/index.vue:96-97` 明文列。
- **影响**：与记账侧 `CmsLedgerUserController.mask/maskPhone` 自相矛盾；后台任一有 `cms:user:list` 权限的人可批量拉取联系方式。
- **整改**：列表统一脱敏（复用 `DesensitizedType` 或移植 `mask/maskPhone`）；明文查看需 `cms:user:contact` 权限 + 用户授权 + 留痕；导出禁带明文。

#### P0-5 无隐私政策 / 注册无协议勾选

- **证据**：App 全仓无「隐私政策/用户协议」页面（`grep 协议|privacy` 无结果）；`register/index.vue` 无勾选框。
- **影响**：第 17 条告知义务缺失；应用市场上架会被驳回。
- **整改**：新增协议页（正文走 CMS 文章，版本号入库）；注册/首次登录强制勾选；`portal_user_agreement` 记录 `doc_type/version/agreed_at/ip`。

### P1（管理有效性）

#### P1-1 隐藏功能不生效（前端兜底覆盖后台配置）

- **证据**：`mine/index.vue:155-177` —— 接口只返回 `visible=1`，但前端把「内置兜底清单里未被配置覆盖的项」又拼回列表（`:170,174`）。
- **后果**：把 `personalize` 设为隐藏后，它仍出现在「更多」页（因为内置清单有它，且不在可见集合里）；即**「隐藏」动作对内置 10 项全部失效**（可见项仍会按配置覆盖名称/顺序）。
- **整改**：区分「配置驱动」与「兜底」——兜底仅在**接口失败**时启用；成功返回后严格以配置为准，缺失即删除。或让接口返回全量 + `visible` 字段，由前端过滤。

#### P1-2 入口配置与 App 路由不一致（死链）

- **证据**：`ledger_app_feature_config` 中 `tip`（赞赏）`visible=1`；`mine/index.vue:214-227` 的 `routes` 无 `tip`，`:242` 的 `todo` 占位数组也无 `tip` → 点击**无任何反馈**。
- **整改**：功能入口表加 `route` 列（后端下发真实路由），后台选择路由而非手填；后台「保存」时校验 App 路由白名单；App 侧对未知 key 统一提示「功能暂未开放」。

#### P1-3 功能入口不能增删、字段不可全编辑、链接无校验

- **证据**：`CmsLedgerAppFeatureController.java:38-71` 只有 `list` + `edit`（无 `POST`/`DELETE`）；UI 只提交 `featureName/sortNum/remark` + 显隐（`appFeature/index.vue:154-164`），后端虽支持 `icon/iconColor/badge` 但 UI 未开放；`remark` 承载任意 URL 且无域名白名单。
- **整改**：补增删接口与权限点；UI 开放图标（从 App 已支持集合选）、颜色、角标；链接做域名白名单 + 必填协议头校验。

#### P1-4 商品类目/售卖渠道/进货渠道无后台

- **证据**：三张表的预设数据在 `zyg_dml_05_ledger.sql:36-58`，但 `/cms/ledger` 无任何对应 Controller；App 侧只允许用户自建（`PortalLedgerSaleChannelController` 等拒绝操作系统预设）。
- **后果**：新增/改名渠道必须改 SQL 发版；运营完全无法自助。

#### P1-5 交易类型无法后台维护

### 6.1 管理边界矩阵（一页看懂谁管什么）

### 6.2 授权链路（推荐 M1：用户主动授权）

```
[App 设置 → 隐私与授权]
   │ 用户选择范围 + 用途说明 + 期限（24h/7d）
   ▼
POST /portal/ledger/data-auth  {scopes:["transaction"], purpose:"客服核对账单", hours:24}
   │ 写入 portal_data_auth（version 对齐隐私政策版本）
   ▼
[后台 用户管理]
   │ 查询个体数据前：assertAuthorized(userId, scope)
   ├─ 无授权 → 403「用户未授权查看该数据」
   └─ 有授权 → 返回脱敏结果 + 写 sys_data_access_log(auth_id)
   ▼
[到期/用户撤回] → 自动失效（定时任务扫描 expire_at，或读取时判空）
```

**M2（备选）**：后台发起授权申请 → App 消息中心收到确认卡片 → 用户点同意。链路更重，适合 B 端协作场景；当前一人公司形态用 M1 足够。

**授权粒度建议**：`transaction`（流水）、`account`（账户余额）、`budget`、`inventory`、`ai`、`profile`（联系方式/画像）。默认一次性全部不勾选。

## 10 可行性复核（v1.1）

### 10.1 总体结论

- **技术可行，无架构级障碍**：字典树管理、`@Sensitive`/`DesensitizedType`、`LogAspect`、`@Scheduled` 任务、MinIO/`sys_file` 文件删除、门户/后台双安全链、61 个测试类均已具备，改造是"在既有范式上复制"，不是新造轮子。
- **真正的约束不是技术**：3 个必须先定的产品决策（授权粒度/有效期/冷静期）+ 2 个外部输入（隐私政策正文、数据保留期限）+ 1 条 SQL 双轨纪律。
- **v1.0 工期偏乐观**：P0 原估 1.5~2 人日，实际约 **5~6 人日**（不含协议文本撰写）；主要低估在"注销删数"和"脱敏改 47KB 页面"。

|---|---|---|---|---|

| P0-2 | 访问审计 | **A** | 复用 `LogAspect` 或手写插入均可；需定「复用 `sys_oper_log` 还是新表」 | 0.5d |

### 10.3 主要风险

1. **授权 gate 改变运营习惯**：后台「用户管理」在无授权时只能看到聚合与"未授权"标记——这是设计意图，但必须有引导文案，否则客服会认为"系统坏了"。
2. **注销不可逆**：建议冷静期内只打标记、到期才物理删除；误删无恢复手段，需二次确认 + 导出引导。
3. **字典化回归成本 > 开发成本**：13 类下拉散落在 App 8 个页面，表单回填、离线缓存、默认值兜底都要过一遍。
4. **SQL 双轨纪律**：漏改 `init-sql` 会让新环境缺表/缺种子（P1-10 就是现成反例）；菜单只能改 `moyun-menu-redo.sql`，不能走增量脚本。
5. **多实例**：若用 `@Scheduled` 做"授权到期/注销清理"，需按项目既有并发保护范式加锁；**更稳的是读时判 `expire_at`，不引入定时任务**。
6. **合规不是纯代码**：访问控制、审计、脱敏可代码化；但告知文本、保存期限、个人信息保护影响评估（PIA）记录、App/算法备案仍需人工完成，代码只能保证"可执行、可追溯"。

### 10.4 建议顺序（相对 v1.0 有调整）

| 序 | 内容 | 工时 | 理由 |
|---|---|---|---|
| 0 | 修 3 个显示 bug + 统一 `db-init`/`init-sql` 口径 | 0.3d | 成本最低、收益立刻可见，且为后续改造清障 |
| 1 | **P0a**：访问审计 + 统一脱敏 + 授权表/接口 + 后台 gate | 2d | 合规红线主体，不依赖外部输入 |
| 2 | **P0b**：注销删数（冷静期）+ 协议页（等文本）+ 快照清洗 | 2~2.5d | 依赖法务文本，可并行等 |
| 3 | **P1a**：入口修复 + 商品类目/渠道后台（含种子）+ 交易类型/反馈类型字典 | 2.5d | 运营获得感最强 |
| 4 | **P1b**：高频字典（仓库/货架/原因/来源/单位） | 1.5d | 库存模块主战场 |

| 6 | **P2** | 按需 | 含评分卡参数化（建议降级为"只影响新查询"） |

### 10.5 本机可验证性

- 工具链：Java 21 + Maven 3.6.3 + Node 24；**MySQL 3306 / Redis 6379 均在运行**；`moyun-server` 有 61 个测试类；后台/App 用 npm（本机无 pnpm）。
