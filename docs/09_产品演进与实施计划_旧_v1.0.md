## 第一部分：项目定位与战略

### 1.1 项目愿景

**墨韵智库**定位于"学习与创作双轮驱动的中文内容社区"，服务于两类核心用户：

1. **爱学习的年轻人**（学生 / 求职者 / 在职进阶者）：通过面试题库、刷题、面经、简历工具、读书获得职业成长。
2. **文学爱好者**（写作者 / 读者 / 读书会成员）：通过专栏连载、读书、创作挑战、读者互动获得创作沉淀与变现。

社区的灵魂是"**沉淀 - 反馈 - 激励**"：
- 沉淀：让学习与创作都能被组织成体系（学习计划、专栏连载），而非零散行为。
- 反馈：让创作者与学习者都能看到读者与同伴的响应（评论、点赞、打赏、关注动态、纠错）。
- 激励：让持续行为获得回报（成长值、徽章、变现、排行榜、权益）。

### 1.2 目标用户画像

#### 画像 A：爱学习的年轻人
| 维度 | 描述 |
|------|------|
| 年龄 | 18-30 岁，大学生到工作 5 年内 |
| 痛点 | 刷题无计划、无错题本、无同伴；面试题无场景感；简历能写但无人指点 |
| 行为 | 高频短时使用（通勤/午休/晚自习），偏移动端 |
| 付费意愿 | 求职期付费意愿高（简历优化、模拟面试、付费面经、内推） |
| 关键诉求 | 进度感、成就感、求职闭环、社群陪伴 |

#### 画像 B：文学爱好者
| 维度 | 描述 |
|------|------|
| 年龄 | 22-40 岁，大学生到中年写作者 |
| 痛点 | 没有专栏做不了系列；写了没人看；想变现但无渠道；找不到同好 |
| 行为 | 低频长时使用（周末/夜晚写作），偏 PC 端 |
| 付费意愿 | 创作者愿为曝光与读者付费（付费阅读分成、专栏会员），读者愿为优质内容付费 |
| 关键诉求 | 系列化运营、读者反馈、变现、创作者身份认同 |

### 1.3 核心价值主张

| 用户 | 价值 |
|------|------|
| 学习者 | "刷题有计划、答题有反馈、学习有同伴、求职有闭环" |
| 创作者 | "写专栏有人追、被读者看见、能获得打赏、被认证为创作者" |
| 读者 | "读得到连载、能与作者对话、能为喜欢的内容付费、有成长记录" |

### 1.4 战略路径选择

**先做"创作社区"，再做"学习社区"**。理由：

1. 创作社区变现路径短（打赏 / 付费阅读 / 会员分成），ROI 高
2. 创作者自带流量（作品传播带来新用户），获客成本低
3. 现有文章 + 读书模块已具备 70% 底座，补"专栏连载 + 变现 + 活动"即可闭环
4. 学习社区需要在线代码运行、AI 模拟面试等重投入，先验证创作社区成立后再上

因此实施顺序为：**阶段一（社区地基） → 阶段二（创作者天堂） → 阶段三（学习者闭环） → 阶段四（社交深化与商业化）**。

### 1.5 成功指标（北极星）

| 阶段 | 北极星指标 |
|------|----------|
| 阶段一 | 7 日留存率、人均会话时长 |
| 阶段二 | 专栏数、付费阅读订单数、打赏笔数 |
| 阶段三 | 日活刷题用户、连续打卡 7 日用户数 |
| 阶段四 | 月付费用户数、创作者分成总金额 |

### 2.2 严重缺口（按优先级）

#### P0 — 阻断社区成立
| 序号 | 缺口 | 影响 |
|------|------|------|
| P0-1 | 个人中心仅 2 个 Tab（文章/收藏） | 用户所有行为无聚合入口，无归属感 |
| P0-2 | 动态 / Feed 流完全缺失 | 关注关系零价值兑现 |
| P0-3 | 私信功能完全缺失 | 用户之间无法沟通，无社区粘性 |
| P0-4 | 消息中心无独立页 | 信息不聚合 |
| P0-5 | 书单-书籍关系 Controller 未实现 | 书单功能形同虚设 |
| P0-6 | 共读活动 4 表已建未启用 | 死代码，社交化读书无法落地 |
| P0-7 | 金句点赞 / 书单点赞接口被删除 | 表已建但闲置，互动残缺 |

#### P1 — 阻断"创作社区"成立
| 序号 | 缺口 | 影响 |
|------|------|------|
| P1-1 | 专栏 / 连载 / 合集功能完全缺失 | 创作者无法系列运营（致命） |
| P1-2 | 创作无任何变现路径（打赏/付费阅读/稿费） | 创作无回报 |
| P1-3 | 创作挑战 / 征文活动功能缺失 | 无运营引流抓手 |
| P1-4 | 草稿 / 文章无版本管理 | 修改无回滚、无对比 |
| P1-5 | 创作数据看板缺失 | 创作者无反馈 |

#### P1 — 阻断"学习社区"成立
| 序号 | 缺口 | 影响 |
|------|------|------|
| P1-6 | 学习计划 / 错题本 / 刷题日历完全缺失 | 刷题无闭环 |
| P1-7 | 在线代码运行环境缺失 | 与 LeetCode 差距大 |
| P1-8 | 简历与职位完全脱节 | 简历工具无法闭环到求职 |
| P1-9 | AI 模拟面试官缺失 | 仅有简历评分 |

#### P2 — 体验与商业化拓展
话题/超话、圈子、@提及、评论楼中楼、黑名单、个性化推荐、移动端 TabBar、签到日历、任务系统、积分商城、VIP 会员中心、文章追更订阅、转载标注、引用关系图。

#### 1.1 个人中心 Tab 扩展

**现状**：仅"我的文章 / 我的收藏"2 个 Tab。

**目标**：扩展为 8 个 Tab。

```
个人中心 Tab
├── 文章（已有）
├── 收藏（已有，扩展为多类型 Tab：文章/题目/书单/金句）
├── 阅读（我的书架 + 阅读历史 + 阅读统计）
├── 学习（我的答题 + 错题本 + 学习计划）

└── 账号（举报 / 反馈 / 消费记录 / 设置入口）
```

**实现**：
- 复用已有 API（书架、答题、面经、简历、关注、成长）
- 新增聚合接口 `GET /portal/user/me/dashboard`（返回各模块统计数字，用于 Tab 角标）

#### 1.2 动态 / Feed 流

**目标**：登录用户在首页 / 动态页看到关注作者的更新聚合。

**技术方案**：推拉结合
- **写时推**：作者发布文章 / 面经 / 新增简历模板 / 创建专栏时，写入"动态事件表"
- **读时拉**：用户打开 Feed 时，拉取关注者最近 N 天的动态事件，按时间排序
- **冷启动**：未关注任何作者时，回落到全站热门动态

**新增表**：

```sql
-- 动态事件表
CREATE TABLE portal_feed_event (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL COMMENT '事件发布者',
    event_type VARCHAR(32) NOT NULL COMMENT 'publish_article/publish_experience/new_column/checkin等',
    target_type VARCHAR(32) NOT NULL COMMENT 'article/experience/column/book等',
    target_id BIGINT NOT NULL COMMENT '目标对象ID',
    content VARCHAR(500) COMMENT '动态摘要',
    created_time DATETIME NOT NULL,
    INDEX idx_user_time (user_id, created_time),
    INDEX idx_type_time (event_type, created_time)
) COMMENT='动态事件流';

-- 用户收件箱（推模式，可选优化）
CREATE TABLE portal_feed_inbox (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_id BIGINT NOT NULL COMMENT '接收者',
    event_id BIGINT NOT NULL COMMENT '动态事件ID',
    created_time DATETIME NOT NULL,
    INDEX idx_user_time (user_id, created_time)
) COMMENT='动态收件箱';
```

**新增 API**：
- `GET /portal/feed/list` — 我的关注动态（分页）
- `GET /portal/feed/hot` — 全站热门动态（未登录或冷启动）

**新增页面**：
- `/feed` — 动态页（首页增加"动态"Tab）

#### 1.3 私信功能

**目标**：1v1 私信会话，未读提醒。

**技术方案**：WebSocket 实时推送 + HTTP 拉取历史
- WebSocket 端点 `/ws/message`，建立连接后接收私信实时推送
- HTTP 接口拉取会话列表、历史消息
- 离线消息存数据库，上线后推送未读

**新增表**：

```sql
-- 私信会话
CREATE TABLE portal_message_session (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    user_a BIGINT NOT NULL COMMENT '用户A',
    user_b BIGINT NOT NULL COMMENT '用户B',
    last_message_id BIGINT COMMENT '最后一条消息ID',
    last_message_time DATETIME COMMENT '最后消息时间',
    unread_a INT DEFAULT 0 COMMENT 'A未读数',
    unread_b INT DEFAULT 0 COMMENT 'B未读数',
    created_time DATETIME,
    updated_time DATETIME,
    UNIQUE KEY uk_users (user_a, user_b),
    INDEX idx_last_time (last_message_time)
) COMMENT='私信会话';

-- 私信消息
CREATE TABLE portal_message (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    session_id BIGINT NOT NULL COMMENT '会话ID',
    sender_id BIGINT NOT NULL COMMENT '发送者',
    receiver_id BIGINT NOT NULL COMMENT '接收者',
    content TEXT NOT NULL COMMENT '消息内容',
```

| PDF | Apache PDFBox 3.0.3（已有） |

### 5.2 关键技术难点与方案

#### 难点 1：Feed 流性能

**问题**：关注 1000 人后，每次拉取 Feed 需聚合 1000 人的事件，慢。

**方案**：推拉结合
- 写时推：发布事件时写入 `portal_feed_event` + 批量写入关注者的 `portal_feed_inbox`（异步队列）
- 读时拉：用户打开 Feed 时直接读 `portal_feed_inbox`，O(N) 复杂度降为 O(1)
- 大 V 特殊处理：粉丝 > 10000 时只写事件表，不写收件箱，读时拉

**优化**：Redis 缓存用户最近 100 条 Feed，避免每次查库。

#### 难点 2：私信实时推送

**问题**：用户离线时消息丢失；高并发下 WebSocket 连接管理。

**方案**：
- WebSocket + STOMP 协议，Spring Boot 已有 `spring-boot-starter-websocket`
- 离线消息存 `portal_message` 表，上线后推送未读
- 连接管理：Redis 存 `user_id → session_id` 映射，支持多端登录
- 消息堆积：单会话保留最近 1000 条，更早的分页查询

#### 难点 3：在线代码运行安全

**问题**：用户提交任意代码，可能恶意攻击服务器。

**方案**：Docker 沙箱
- 每次运行启动一个临时容器，限制内存 256MB / CPU 1 核 / 时间 5s
- 容器内无网络访问
- 执行完销毁容器
- 限制用户运行频率（每分钟 5 次）

#### 难点 4：付费阅读的防爬防泄露

**问题**：付费内容可能被截图、被复制。

**方案**：
- 服务端校验购买状态，未购买只返回试读部分
- 内容水印（用户 ID + 时间戳暗水印嵌入文字）
- 限制单 IP 访问频率
- 前端禁用右键 / 复制（仅前端防护，非强保护）

#### 难点 5：AI 模拟面试的成本控制

**问题**：LLM API 调用成本高，免费用户滥用。

**方案**：
- 免费用户每日 3 次模拟面试
- VIP 用户每日无限次
- 缓存 AI 提问模板，减少重复调用
- 监控单用户 API 调用成本，异常告警

#### 难点 6：成长体系埋点的全局一致性

**问题**：现有成长事件埋点散落各处，易遗漏。

**方案**：统一 AOP 切面
- 定义 `@GrowthEvent(type="publish_article")` 注解
- 在 Service 方法上加注解，AOP 切面统一记录成长日志
- 修改成长规则时无需改业务代码

#### 难点 7：Flowable 工作流与业务的耦合

**问题**：征文评审、认证审核流程多变，硬编码不可维护。

**方案**：
- 流程定义独立维护，业务表只存 `process_instance_id`
- 业务状态与流程节点通过 `task_complete` 事件同步
- 后台提供流程设计器（Flowable 自带）

### 5.3 前端架构调整

- **路由分组**：`/feed`、`/messages`、`/columns`、`/column/*`、`/learn`、`/creator`、`/vip`、`/contests` 等新增顶级路由
- **状态管理**：Feed、私信、消息使用 Pinia store
- **组件库**：复用现有 Tailwind 体系，不引入新 UI 库
- **移动端**：响应式布局，移动端底部 TabBar

### 5.4 后端架构调整

- **模块划分**：新增 `portal/feed`、`portal/message`、`portal/column`、`portal/tip`、`portal/contest`、`portal/creator`、`portal/learn`、`portal/job`、`portal/circle`、`portal/task`、`portal/shop` 等 Controller
- **Service 层**：每个模块独立 Service，跨模块调用通过事件总线（Spring ApplicationEvent）
- **定时任务**：每日凌晨统计昨日数据、艾宾浩斯复习提醒、创作者结算

## 第八部分：风险与对策

### 8.1 技术风险

| 风险 | 等级 | 对策 |
|------|------|------|
| Feed 流性能瓶颈 | 高 | 推拉结合 + Redis 缓存 |
| WebSocket 连接管理复杂 | 中 | Spring WebSocket + Redis 分布式 session |
| Docker 沙箱逃逸 | 高 | 限制资源 + 无网络 + 限制频率 + 镜像定期更新 |
| LLM API 成本失控 | 中 | 频率限制 + 缓存 + 监控告警 |
| 表结构变更影响线上 | 中 | AddColumnIfNotExists 存储过程 + 灰度发布 |

### 8.2 业务风险

| 风险 | 等级 | 对策 |
|------|------|------|
| 创作者数量不足，专栏冷清 | 高 | 官方先建精品专栏 + 邀请种子创作者 + 流量倾斜 |
| 学习者付费意愿低 | 中 | 先免费验证留存，再引入付费功能 |
| 用户对付费阅读抵触 | 中 | 试读机制 + 限时折扣 + 退款保障 |

### 8.3 合规风险

| 风险 | 等级 | 对策 |
|------|------|------|
| 打赏 / 付费涉及资金流转 | 高 | 接入第三方支付（微信 / 支付宝），平台不碰资金池 |
| 创作者分成税务 | 高 | 接入第三方代征个税服务（如灵工平台） |
| 用户生成内容违规 | 高 | 接入内容审核 API + 人工审核 + 举报闭环 |
| 个人信息保护 | 高 | 隐私协议 + 数据加密 + 最小化采集 |

### 8.4 内容风险

| 风险 | 等级 | 对策 |
|------|------|------|
| 抄袭 / 洗稿 | 中 | 接入查重 API + 举报机制 + 信用分 |
| 低质内容泛滥 | 中 | 审核机制 + 算法降权 + 举报 |
