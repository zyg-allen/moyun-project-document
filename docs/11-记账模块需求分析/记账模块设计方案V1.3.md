## 一、文档目的与范围

本文档为「个人资产管理记账」模块的工程落地方案，覆盖：

- 与现有墨韵智库系统的集成架构（用户体系、认证、后端模块、管理端）

- 修正需求书后的完整数据模型（6 张核心表）

- 记账联动核心逻辑（事务边界、余额一致性）

- App 端 API 设计（/portal/ledger/\*\*）

- uni-app 多端工程设计

- 分阶段实施计划与四同步交付物清单

**产品定位回顾**：以「资产/负债」为核心视角的个人财务管理工具，核心价值「让用户用一个数字看清自己的全部身家」，解决操作复杂、记账无明细、总数不联动三大痛点。

**范围外声明**：需求书 V1.1 第六章商业化规划（会员增值体系、合规金融导流、运营投放）属运营层面，不在本工程方案范围内；多账本共享会员权益明确**不做**（见 V1.2 修订记录：与产品"全局净资产"定位口径冲突，未来如有真实需求再立项设计）。

## 三、用户体系对接设计

### 3.1 用户 ID 口径（重要）

\**所有 ledger\_* 表的 user\_id 一律使用 `portal_user.id`（门户用户主键）\*\*，即 `PortalSecurityUtils.getUserId()` 的返回值。

> ⚠️ 注意：`PortalUser` 实体存在双 ID——自身主键 `id` 与关联后台的 `userId`（sys\_user.user\_id）。门户业务（文章 authorId 等）取的是前者；而 `pay_user_account` 语义上关联 sys\_user。两模块口径不同，开发时严禁混用，ledger 模块统一用 portal\_user.id。

### 3.2 登录链路

```
小程序 uni.login → code
    ↓
POST /portal/ledger/auth/wechat-login  （新增端点，归属用户中心维护，ledger 模块不建用户表）
    ↓ 后端调微信 code2Session 换 openid
    ├─ openid 已绑定 portal_user → 签发 JWT（复用门户 Token 体系）
    └─ 未绑定 → 自动注册新 portal_user（手机号可选补绑）→ 签发 JWT
    ↓
后续所有 /portal/ledger/** 请求携带 JWT，走门户安全过滤链（需在 PortalSecurityConfig 增加 /portal/ledger/** 鉴权规则）
```

**跨模块依赖（Phase 1 显式依赖项）**：微信登录端点 + `portal_user_wechat` 绑定表（openid 唯一索引）归属用户中心改造，需在 ledger Phase 1 排期前与用户中心确认；微信小程序 appid 申请为前置条件（见 TODO）。

### 3.3 账号打通说明

- 记账用户与门户（H5/社区）用户**同一账号体系**：同一 `portal_user.id` 在门户端和记账端看到各自模块的数据

- 记账模块**不含**注册/登录/找回密码等账号管理功能，全部依赖门户用户中心

## 四、数据模型设计（核心修正）

### 4.1 需求书修正说明

| 需求书原设计                  | 修正为                                  | 修正原因                                |
| ----------------------- | ------------------------------------ | ----------------------------------- |
| 表名 `asset_account` 等    | `ledger_` 前缀                         | 与 `pay_` 前缀惯例一致，避免命名冲突              |
| 流水表名 `transaction`      | `ledger_transaction`                 | `transaction` 是 MySQL 保留字           |
| 金额 `DECIMAL(18,2)`      | `BIGINT`（单位：分）                       | 全项目金额硬规范（见 pay 模块），避免浮点误差，展示层转元     |
| `created_at/updated_at` | `create_time/update_time`            | 与全库既有命名规范一致                         |
| 每用户复制系统分类               | `user_id=0 + is_system=1` 表示系统预设     | 一份预设数据全量复用，支持后台统一维护                 |
| 流水表无余额快照                | 补 `balance_after` + 乐观锁 `version`    | 修改/删除流水时余额回滚与并发安全的关键依据              |
| 净资产无历史数据                | 新增 `ledger_net_worth_snapshot` 每日快照表 | 当前余额是"现在时"，无快照则净资产趋势图与涨跌标识无法实现      |
| 5 种记账类型                 | 增加 `adjust`（余额校准）为第 6 种              | 用户账实不符需校准余额；直接改 balance 不留痕会破坏全明细追溯 |

### 4.2 BaseEntity 不继承约束（详细说明）

ledger 全部实体类**不继承 BaseEntity**，原因：

1. **字段语义**：BaseEntity 含 `createBy/updateBy/remark/delFlag` 六个业务字段，而记账数据为 C 端用户自助产生，数据归属者即 user\_id 本人，无"操作人"审计语义；pay 模块全部表同样只有 `create_time/update_time`
2. **继承即报错**：实体继承 BaseEntity 而表无 `create_by` 等列时，MyBatis-Plus 生成的 SQL 会携带这些列，运行时 SQL 错误
3. **del\_flag 逻辑删除冲突**：BaseEntity 的 `delFlag` 标注 `@TableLogic`，继承后 MP 对所有查询自动追加 `WHERE del_flag='0'`。流水表"删除=冲正+status=0"是业务态逻辑删除，必须自管 `status` 字段，不能混用 MP 逻辑删除机制

### 4.3 表结构总览

共 6 张表，统一前缀 `ledger_`，引擎 InnoDB，字符集 utf8mb4\_general\_ci。**单账本模型，不含 book\_id**（V1.2 决策）。

#### 4.3.1 资产账户表 `ledger_asset_account`

| 字段                          | 类型                     | 必填    | 说明                                                                          |
| --------------------------- | ---------------------- | ----- | --------------------------------------------------------------------------- |
| id                          | BIGINT AUTO\_INCREMENT | ✅     | 主键                                                                          |
| user\_id                    | BIGINT                 | ✅     | 门户用户ID（portal\_user.id）                                                     |
| name                        | VARCHAR(100)           | ✅     | 账户名称，如“招商银行储蓄卡”                                                             |
| type                        | VARCHAR(20)            | ✅     | cash/savings/ewallet/stored\_value/investment/fixed\_asset/receivable/other |
| balance                     | BIGINT                 | ✅ 默认0 | 当前余额（分）                                                                     |
| valuation                   | BIGINT                 | NULL  | 估值（分；投资/固定资产用，可≠balance）                                                    |
| include\_in\_total          | TINYINT                | ✅ 默认1 | 是否计入总资产                                                                     |
| icon                        | VARCHAR(50)            | NULL  | 图标                                                                          |
| hide\_balance               | TINYINT                | ✅ 默认0 | 是否隐藏余额（隐私模式）                                                                |
| sort\_order                 | INT                    | 默认0   | 排序                                                                          |
| status                      | TINYINT                | ✅ 默认1 | 1=启用 0=停用归档（删除即归档，流水永久保留）                                                   |

| liability\_id               | BIGINT                 | NULL  | 关联负债账户（还款/借款）                                               |
| target\_account\_id         | BIGINT                 | NULL  | 转账目标资产账户                                                    |
| balance\_after              | BIGINT                 | NULL  | 主账户交易后余额快照（分；与 pay\_ledger\_entry 一致）                       |
| target\_balance\_after      | BIGINT                 | NULL  | 转账目标账户交易后余额快照                                               |

| description                 | VARCHAR(200)           | NULL  | 备注                                                          |
| transaction\_date           | DATE                   | ✅     | 交易日期（默认当天）                                                  |
| transaction\_time           | TIME                   | NULL  | 交易时间                                                        |
| merchant                    | VARCHAR(100)           | NULL  | 商户名称                                                        |
| voucher\_url                | VARCHAR(500)           | NULL  | 凭证截图URL（20260903-02 增量：复用门户文件服务 /portal/file/upload，仅存 URL） |
| is\_budget                  | TINYINT                | ✅ 默认1 | 是否计入预算（adjust 默认 0 不计入）                                     |
| status                      | TINYINT                | ✅ 默认1 | 1=正常 0=已删除（逻辑删除，余额冲正后归档）                                    |
| client\_uuid                | VARCHAR(64)            | NULL  | 客户端幂等键（离线同步防重复提交，Phase 4）                                   |
| create\_time / update\_time | DATETIME               | ✅     | 时间戳                                                         |

索引：`idx_user_status_id (user_id, status, id)`（首页最近流水：`WHERE user_id=? AND status=1 ORDER BY id DESC LIMIT 20`）、`idx_user_date (user_id, transaction_date)`、`idx_account (account_id)`、`idx_liability (liability_id)`、`uk_client_uuid (client_uuid)`

> 设计要点：流水**不物理删除**，删除 = 逻辑标记（status=0）+ 反向冲正余额；保证历史报表可追溯（需求书“删除记录余额自动回退”）。

#### 4.3.6 净资产每日快照表 `ledger_net_worth_snapshot`（新增）

净资产趋势图与首页涨跌标识的数据来源（当前余额是"现在时"，无快照则历史趋势无法回溯）。

| 字段               | 类型                     | 必填 | 说明                    |
| ---------------- | ---------------------- | -- | --------------------- |
| id               | BIGINT AUTO\_INCREMENT | ✅  | 主键                    |
| user\_id         | BIGINT                 | ✅  | 门户用户ID                |
| snap\_date       | DATE                   | ✅  | 快照日期（每日 00:10 定时任务生成） |
| total\_asset     | BIGINT                 | ✅  | 总资产（分）                |
| total\_liability | BIGINT                 | ✅  | 总负债（分）                |
| net\_worth       | BIGINT                 | ✅  | 净资产（分）                |
| create\_time     | DATETIME               | ✅  | 创建时间                  |

生成规则：定时任务逐用户聚合 `status=1 AND include_in_total=1` 的账户余额落一行；当日有记账变动的用户实时更新当日行（事务内 upsert），无变动保持定时值。

> 统计口径：首页净资产/总资产/总负债 = 账户表现值聚合；涨跌对比 = 与昨日快照比较；收支/预算 = 流水表按 `transaction_date + status=1 + is_budget=1` 实时聚合。跨月修改流水后统计天然自动重算（满足需求书边缘场景 2）。

## 五、记账联动核心逻辑（事务设计）

### 5.1 联动规则矩阵

| 记账类型         | 资产账户                                                    | 负债账户                         | 净资产        |
| ------------ | ------------------------------------------------------- | ---------------------------- | ---------- |
| income 收入    | account\_id 余额 **+amount**                              | —                            | +amount    |
| expense 支出   | account\_id 余额 **-amount**                              | —                            | -amount    |
| transfer 转账  | account\_id **-amount**，target\_account\_id **+amount** | —                            | 不变         |
| repayment 还款 | account\_id 余额 **-amount**                              | liability\_id 欠款 **-amount** | 不变（资产负债同减） |
| borrow 借款    | account\_id 余额 **+amount**                              | liability\_id 欠款 **+amount** | 不变（资产负债同增） |
| adjust 余额校准  | account\_id 余额 **设为指定值**（差额=amount，可正可负）                | —                            | 随差额        |

> 特例 1：信用卡消费（不动储蓄卡）= borrow 且 account\_id 为 NULL，仅负债 +amount，净资产 -amount。
> 特例 2：adjust 用于账实不符校准，差额自动生成流水留痕，用户不可直接编辑 balance 字段。

**边界校验规则**：

- 还款金额 > 负债当前欠款：**拒绝**，提示"还款金额不能超过当前欠款 ¥x"（溢缴款场景本期不支持）

- 转账两个账户不能相同；金额 > 0

- 记账账户/负债必须属于当前用户（user\_id 归属校验防水平越权）

### 5.2 事务边界（项目硬约束：多表写必须单 @Transactional 服务方法）

```java
@Transactional(rollbackFor = Exception.class)
public Result<Long> createTransaction(Long userId, TransactionCreateDTO dto) {
    // 1. 校验账户归属（user_id 防越权）与乐观锁 version
    // 2. 按类型计算双边余额变动（金额守恒校验：转账前后总资产不变）
    // 3. UPDATE ledger_asset_account / ledger_liability_account（带 version 条件）
    // 4. INSERT ledger_transaction，写入 balance_after / target_balance_after / liability_balance_after 快照
    // 5. 负债结清判定：balance = 0 → settle_flag 置 1（不计入当前总负债）
    // 6. upsert 当日 ledger_net_worth_snapshot
}
```

### 5.3 修改/删除流水的余额回滚算法

```
修改：旧记录反向冲正（按旧金额逆向执行 5.1 矩阵）→ 新记录正向重放 → 更新快照
删除：旧记录反向冲正 → 逻辑删除（status=0）→ 快照保留在流水行
```

## 九、安全与隐私设计

| 层面       | 方案                                                                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| 传输       | 全链路 HTTPS + JWT（有效期与门户一致）                                                                                                                  |
| 加密边界（重要） | **金额字段不加密**（BIGINT 分值无业务语义，且 SUM 聚合/索引依赖明文）；**敏感文本字段加密**：账户名称、备注、商户名采用 AES-GCM 加密列 + 脱敏列双列模式（参考 `pay_user_bank_card`）。报表统计仅用金额+类型聚合，不受加密影响 |
| 隐私模式     | 端侧金额隐藏（`hide_balance` + 前端全局开关）；App 端生物识别锁（Phase 4）                                                                                        |
| 越权防护     | 所有查询/变更强制 `user_id` 归属校验（防水平越权），复用统一权限校验                                                                                                   |
| 审计       | 管理端仅可见脱敏聚合数据，不可见单用户记账明细（隐私域红线）                                                                                                             |

> 需求书 AES-256 全量落库加密按上述「边界加密」落地：全量加密将破坏 SQL 聚合与索引能力，此为工程可行性与需求的折中，已在评审中说明。

## 十六、AI 财务分析设计（2026-09-04 增补，V1.3 → V1.4）

### 16.1 功能概述

「分析」Tab 页（第五个 Tab，替代原资产/负债分离 Tab）：基于用户记账行为 + 用户画像，输出数据展示、风险提示与个性化建议。

### 16.2 用户画像（与门户共用 portal_user 表）

| 维度     | 字段          | 来源/说明                                  |
| ------ | ----------- | -------------------------------------- |
| 身份标签   | identity_tag | 新增字段，字典 `ledger_identity_tag`（学生/上班族/自由职业/个体经营者/退休/其他），后台「系统管理→字典管理」可维护 |
| 职位/公司  | position/company | 门户既有字段，前台/门户双端同步维护                   |

### 16.3 分析内容

- **财务健康指标**（规则引擎）：总资产/总负债/净资产、资产负债率、月均收入/支出、月还款额、还款压力（月还款/月收入）、储蓄率、连续入不敷出月数
- **收入来源结构**：按收入分类统计金额与占比，识别收入单一风险，给出「拓展兼职技能」等建议
- **债务风险提示**（分级 high/medium/low）：车贷/信用卡还款提示、还款日临近（repayment_day）、还款能力不足（月还款 > 月收入 50%）、资产负债率过高（>80%）
- **理财建议**：长期入不敷出（deficitMonths ≥ 3）触发收支平衡/储蓄规划建议；无收入有支出触发补记提示

## 附录 B：金额安全计算规范（V1.31 增补 · 2026-09-04）

> 背景：金额 BIGINT 分单位 + JS 字符串 Long 序列化 + 浮点乘法三条链路叠加下，若某一环处理不当会出现「负号丢失 / 浮点精度 / 千分位回写 NaN / 100 倍入库」四类隐患，统一规范如下。

### B.1 存储口径（全项目硬约束）

| 维度 | 规则 |
| --- | --- |
| 数据库字段 | 金额一律 BIGINT，单位 **分**；禁止 DECIMAL/DOUBLE |
| Entity 字段类型 | Long balance / Long principal / Long amount / Long valuation |
| JSON 序列化 | Jackson 全局 WriteNumbersAsStrings = true，所有 Long → JSON 字符串；避免 JS Number.MAX_SAFE_INTEGER 之上精度丢失 |

### B.2 前端转换（强制走 utils/money.js，ESLint 禁手写 *100）

| 场景 | 正确用法 | 禁止写法 |
| --- | --- | --- |
| 表单输入 元 → 提交 分 | yuanToCent(form.amountStr) | Number(v) * 100、parseFloat(v) * 100 |
| 后端分 → <input> 回显（无千分位） | centToYuan(cent) | centToAmount()（会带千分位，再次提交变 NaN） |
| 展示卡片金额（可能为负：合计/净资产/账户余额） | centToAmount(cent)（保留负号） | 自己 .toFixed(2) |
| 语义前缀型展示（+收入 / -支出 / 欠 ¥ / 溢缴） | 前缀 + centToAbsAmount(cent) | 前缀 + centToAmount（若数值负会出现 +-xxx） |
| 数组聚合（分） | safeSumCents(list, 'balance') | rr.reduce((s, x) => s + x.balance, 0) — x.balance 是字符串 Long 会变拼接 |

### B.3 yuanToCent 处理矩阵（字符串安全解析实现）

| 输入 | 输出（分） | 备注 |
| --- | --- | --- |
| '' / null / undefined | 0 | 空判 |
| '2200' | 220000 | 整数元 |
| '22.5' | 2250 | 自动补第二位 0 |
| '1,234.56' | 123456 | 先剥千分位 |
| '-88.88' | -8888 | 保留符号 |
| '1.005' | 101 | 第三位小数 ≥5 进一（浮点乘会错算成 100） |
| 'abc' | 0 | 非法 → 兜底 0 + Number 解析 fallback |
| > 9e14（约 9 万亿元） | 0 | 上限保护，防止溢出 |

### B.4 后端入库边界（纵深防御第二道闸）

> 即使前端出现疏漏（yuanToCent 未调/错传负值/字段级改包请求），Controller 在 create 入口按分单位做非负 + 上限校验：

- 资产 initialBalance：  ≤ cent ≤ 1_000_000_000_000 (100亿元)
- 负债 initialBalance：同上
- 负债 monthlyPayment：  ≤ cent ≤ 10_000_000_000 (1亿元)
- 超范围一律返回 AjaxResult.error "xxx 超出允许范围，请确认金额单位"

流水联动（转账/还款/借款/adjust）走 Service 层，不强制非负（例：adjust 校准可正可负；信用卡溢缴使余额暂时为负），业务规则由 Service 按类型矩阵把控。

### C.4 金额单位复核（FAQ · 固化到设计）

Q: API 返回 `"balance":"22200"`，页面显示 222.00，是不是少了 100 倍？
A: 否。项目统一口径 BIGINT 存"分"，22200 分 / 100 = 222.00 元 ✓。若业务要存 22200 元，则 DB 应 = 2,220,000 分，页显 "22,200.00"。出现 100x 不匹配说明录入时未走 yuanToCent 转换或旧数据非规范入库，请按 devlog v11.23「三、处理办法」修正。
